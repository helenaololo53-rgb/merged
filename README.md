# Контроль почты — Проблемные письма (объединённое расширение)

Одно расширение вместо двух. В нём объединены:

- **«Взять на контроль»** — захват открытого письма в Google Таблицу (форма в
  попапе: тема, номер ЗП/перемещения, склад, вид, поставщик, документ, комментарий,
  дата; авто-подстановка склада и вида по словарям меток).
- **«Проблемные письма»** — выезжающая панель прямо в Яндекс Почте со списком
  проблемных писем из той же таблицы: возраст на контроле, сортировка/фильтр по
  складу, комментарии (пишутся обратно в таблицу), кнопка «Выполнено», поиск и
  переход к последнему письму по теме через внутренний API почты, бейдж-счётчик.

**Главное:** обе функции теперь берут номера колонок из **одних настроек**
(`fieldConfig`). Задаёте колонку один раз — её используют и захват, и панель.

## Единые настройки колонок

Настройки → карточка «Поля и колонки таблицы». Каждому полю задаётся буква колонки
(перетаскиванием меняется порядок, галочкой — вкл/выкл). Значения по умолчанию:

| Поле                    | Колонка |
|-------------------------|---------|
| Тема письма             | A       |
| Номер ЗП/Перемещения    | B       |
| Склад                   | C       |
| Комментарий             | D       |
| Вид                     | E       |
| **Выполнено (галочка)** | **F**   |
| Дата письма             | G       |
| Поставщик               | H       |
| Документ                | I       |
| **Метка**               | **J**   |

> Колонка **«Выполнено (галочка)»** — служебная для панели: по ней панель прячет
> закрытые письма и ставит отметку кнопкой «Выполнено». В форме захвата она не
> вводится. Подгоните все буквы под свою реальную таблицу — это делается один раз.
>
> Колонка **«Метка»** тоже заполняется сама: в неё пишется метка плашки, на которую
> бросили письмо (или выбранная в форме захвата). По ней счётчик и кнопка 🏷️ каждой
> плашки работают только со своими письмами. Строки без метки (добавленные до
> появления колонки) считаются письмами **первой** метки списка.

Значения по умолчанию (таблица, лист, колонки) лежат в [defaults.js](defaults.js) —
единый источник для `background.js`, `options.js` и `popup.js`.

## Метки и язычки в почте

Настройки → карточка «Метки на письме». Метки задаются **списком**: каждая метка —
это свой язычок (плашка) в почте, названный её именем. Порядок в списке = порядок
язычков сверху вниз (перетаскивание за «⠿» или кнопки ▲▼).

- **Клик по язычку** — открывает панель. Панель одна на все метки, но подписывается
  именем открывшего её язычка и показывает **его** письма (когда меток больше одной).
  Клик по соседнему язычку при открытой панели просто переключает её на другую метку.
- **Перетаскивание письма на язычок** — письмо уходит в таблицу и получает **эту**
  метку; панель при этом не распахивается.
- **Кнопка 🏷️ на язычке** (появляется, когда меток больше одной) — синхронизирует
  метку с таблицей, не открывая панель:
  ставит её на невыполненные письма **своей** метки, снимает со всех остальных строк
  таблицы (выполненных и писем соседних язычков) и отдельно спрашивает про письма
  с этой меткой, которых в таблице нет вообще. Пока метка одна, кнопка живёт в шапке
  панели, как раньше.
- **Счётчик на язычке** — число невыполненных писем именно его метки.
- **Alt+Y (форма захвата)** — ставит первую метку списка; если меток несколько, под
  формой появляются чипсы выбора метки.
- **«Выполнено»** — снимает с письма метку из колонки «Метка»; если она пуста
  (старая строка), снимает все метки списка, чтобы не осталось хвоста.

Настройки хранятся в ключе `labelNames`; старый ключ `labelName` продолжает читаться
(при первом открытии настроек одиночная метка сама превращается в список из одной).

## Один путь добавления строки

И форма «Взять на контроль» (Alt+Y), и перетаскивание письма на язычок шлют в
`background.js` одно и то же сообщение `pm-append`. Значит, у них одинаковые:

- порядок и набор колонок (`buildColMap`);
- извлечение номера ЗП/перемещения из темы — **первое** вхождение вида `0000-0342359`;
- проверка дублей — по номеру **или** по теме среди невыполненных строк.

Раньше попап писал в таблицу сам, со своей проверкой и своим извлечением номера:
на теме с двумя номерами каждый способ брал свой, дубль не находился, и одно письмо
попадало в таблицу дважды.

## Если почта отвечает AUTH_NO_AUTH

Запросы к web-api переигрываются «конвертом», снятым с настоящего запроса почты
(там лежит ключ сессии `_ckey` и заголовки). Конверт берётся **целиком от одного
запроса** и всегда самый свежий: смешивать тело одного запроса с заголовками
другого нельзя, а придерживать старый — значит однажды получить протухший ключ.

Если почта всё же ответила `AUTH_NO_AUTH`, расширение лечится само: сбрасывает
конверт, нажимает «Проверить новые письма», ждёт свежий конверт и повторяет запрос.
Именно это выглядело как «метка ставится через раз». Если и после этого почта
отклоняет запросы, в сообщениях появляется подсказка обновить страницу почты (F5).

## Почему метка «появляется только после F5»

Яндекс не перерисовывает в уже отрисованном списке метку, поставленную через API —
он про неё просто не знает. Поэтому расширение подталкивает почту обновиться:
кнопка «Проверить новые письма» → событие возврата фокуса вкладке → клик по текущей
папке. После перетаскивания это проверяется по факту: если через пару секунд метки на
строке письма нет, список обновляется принудительно. После массовой простановки
кнопкой 🏷️ в отчёте есть кнопка **«Обновить почту»** — на случай, если и это не
помогло.

### Одна точка обновления (2.92)

До 2.92 «подтолкнуть почту» умели **десять** разных мест, и у каждого был свой
сторож: `syncMailQuietly`, `nudgeYandexRefresh`, `forceMailListRefresh`, догон
отложенного, переснятие конверта, уборка «хвостов» и так далее. Они не знали друг о
друге, и каждая версия чинила один симптом, заводя другой: сторож сужали ради «метка
не появляется» — получали «письмо закрылось посреди чтения»; расширяли обратно —
возвращался первый.

Теперь путь один — `requestMailRefresh(повод, { level, force })`, и правила у него
тоже одни:

| Что на экране | Кнопка почты | Клик по папке |
|---|---|---|
| Открыто письмо | не жмём (отложим до закрытия) | нет |
| Результаты поиска | **жмём** — оттуда она не выбрасывает | нет |
| Идёт переход панели к письму | не жмём **никогда**, даже по `force` | нет |
| Ничего из перечисленного | жмём | да, если запросили `level: 'list'` |

Плюс две вещи, которых раньше не было:

- **Одно отложенное действие на панель.** Десять поводов, пришедшихся на время чтения
  письма, дают одно нажатие при закрытии, а не десять подряд.
- **Схлопывание.** Из очереди подряд идущих просьб выполняются две: первая сразу и
  последняя в конце полуторасекундного окна. Прогон «обновить все» на семи плашках
  раньше жал кнопку до восьми раз подряд (по разу на плашку плюс уборка «хвостов»),
  одно перетаскивание — трижды за три секунды. Это и выглядело как «всё мигает».

  Именно две, а не одна. Сначала просьба внутри окна просто выбрасывалась — и
  съедала ту, которая важнее всех, последнюю: при перетаскивании второе обновление
  приходит через доли секунды после первого, уже ПОСЛЕ дозаливки метки и пометки
  писем прочитанными. Пропадало оно — и на экране оставалось состояние до дозаливки.

Строка «идёт переход панели» в таблице — это исправление регрессии 2.91. Там сторож
сузили до одного лишь открытого письма и вместе с этим, не заметив, сняли защиту с
собственной многошаговой навигации панели (клик по папке → ожидание списка →
прокрутка → поиск). Нажатие посреди этой цепочки уводило с того экрана, на котором
следующий шаг собирался работать.

Там же в отчёте показывается причина, если что-то не применилось: ответ почты, не
похожий на успех, сначала перепроверяется по факту (метка на письме уже есть?) и
только потом считается ошибкой.

## Откуда берётся тема письма

Тема снимается со строки списка в таком порядке: узел темы в разметке → `aria-label`
строки → самая длинная видимая строка. Первый источник даёт ровно тему, а вот в
`aria-label` почта перечисляет ещё отправителя, метки, папку и время: в результатах
поиска они идут ПОСЛЕ темы, и тема уезжала в таблицу как «Дёке-Запад ООО, 10:41» —
по такой строке письмо потом не находилось.

Поэтому узел темы теперь приоритетнее `aria-label`, а из `aria-label` вырезаются
отправитель, метки, папка и дата — где бы они ни стояли. Хвост со временем или датой
дополнительно срезается со всех вариантов, в том числе при поиске письма: строки,
записанные до этой правки, ищутся по очищенной теме и работают без ручной правки
таблицы.

## Дата письма и метка на всю переписку

В колонку «Дата письма» пишется дата **последнего** письма ветки — по ней видно,
когда по вопросу были последние движения. Метка при перетаскивании вешается на **всю
переписку**: id берутся и из ответа поиска (там вся ветка), и со строк списка. Раньше
у свёрнутой ветки метку получало одно письмо — то, которое перетащили.

## Кнопка «Выполнено» у открытого письма

Плашка того же вида, что и язычки меток, стоит под ними и появляется, **только если
на открытом письме есть одна из настроенных меток** — иначе нажимать её бессмысленно:
строки такого письма в таблице нет.

## Почему id письма у каждого сотрудника свои

В Яндекс.Почте идентификаторы письма и переписки выдаёт **почтовый ящик**: одно и то
же письмо у разных сотрудников имеет РАЗНЫЕ id. Поэтому id, сохранённый одним
человеком, во второй почте не значит ничего — синхронизация меток у сменщицы уходила
не на то письмо.

В ту же колонку рядом с id пишется **время письма** меткой `ts:<миллисекунды>` — оно
одинаково во всех ящиках. Если id чужой, переписка опознаётся по времени: два письма
с одинаковой темой в один день (13:31 и 13:34) различаются надёжно. Строкам, добавленным
до этой версии, время дописывается автоматически при первой синхронизации меток.

## Метка ставится на ВСЮ ветку, а не на одно письмо

Метка ставится списком id — теми письмами ветки, которые известны на момент
перетаскивания. Этого не всегда хватает:

- у **свёрнутой** ветки часть писем вообще не отрисована на странице;
- поиск по номеру возвращает только те письма, где этот номер есть, — ответы без
  номера в выдачу не попадают;
- ответ в переписку мог прийти секундой позже перетаскивания.

Со стороны это выглядит как «метка встала только на первое письмо».

Поэтому сразу после простановки расширение **спрашивает всю ветку у почты** (один
запрос по её id) и дописывает метку тем письмам, у которых её нет. Дописало — так и
говорит: «Метка «⁉️Архив» поставлена (на всю ветку, дописано писем: 2)». Спросить
ветку не удалось — молча выходим, хуже не станет.

И **после дозаливки почта синхронизируется ещё раз**. Дозаливка идёт после первой
синхронизации, значит помеченные ею письма почта на экране ещё не показывает — без
второго захода выходило ровно то, на что жаловались: в журнале «дописываю метку на
письма ветки — 3 шт.», письма в почте помечены, а на строках ветки плашек нет, пока
не обновишь страницу.

## Метка не снимается с письма, которое просто не удалось опознать

В конце прогона расширение само снимает «хвосты» — метки с писем, которых в таблице
нет. Это делается **фоном и без спроса**, поэтому цена ошибки здесь высокая: лишняя
метка не мешает никому и будет предложена в следующий прогон, а снятая по ошибке
теряется молча и навсегда.

Две дыры, через которые под снятие могло попасть живое письмо:

1. **Письма своей же строки не были защищены.** Их id попадали в список «метка
   положена» только окольным путём — через запрос ветки по её id. Не удалось спросить
   ветку (почта не ответила, id ветки в строке нет) — и письма собственной строки
   уходили в «хвосты». Теперь всё, что опознано за строкой, защищается сразу, включая
   **слабые совпадения**: ставить метку по ним нельзя, а снимать по недостатку улик —
   тем более.
2. **Снятие шло даже после неполного прогона.** Если хоть одну строку разобрать не
   удалось, мы не знаем, чьи это письма, — и «хвостом» могло оказаться письмо живой
   строки. Теперь при любой неразобранной строке снятие пропускается целиком, а в
   консоль пишется почему.

Оба случая становились вероятнее, когда из строки пропадали id (см. ниже) — тогда
опознавать было нечем.

## Колонка «ID письма»: дописывается, а не переписывается

Да, «Обновить метки» **дописывает** эту колонку — и это задумано: строке, заведённой
до появления времени письма или id ветки, прогон добавляет недостающее, чтобы в
следующий раз опознать её без поиска. Но делал он это **перезаписью**: собирал
значение из того, что вернул поиск ПРЯМО СЕЙЧАС, и клал поверх прежнего.

Поиск возвращает не всегда одно и то же — часть писем ветки может не попасть в
выдачу, — и тогда из строки **пропадали id, которые уже были**. Переписка от этого не
уменьшается, значит и список id уменьшаться не должен.

Теперь только дополняется:

- **прежние id сохраняются всегда**, новые дописываются в конец;
- **время письма не переписывается** — своё у строки точнее найденного сейчас;
- **id ветки не дублируется обычным id**. У переписки из одного письма это одно и то
  же число, и в строке оно оказывалось дважды:
  `t194217733931157609,194217733931157994,194217733931157992,194217733931157609,…`
- **чужие строки не трогаются вовсе.** Если колонку заполнял другой ящик (пометка
  `u:<uid>`), его id для нас всё равно бесполезны, а перезаписать их своими — значит
  отобрать их у сменщицы: у неё перестанет работать опознание по id;
- **если дописывать нечего, запись не делается** — незачем плодить правки в истории
  таблицы (именно так и вышло, что прогон разом переписал десяток строк).

## Колонка «ID письма» — какая переписка имеется в виду

Одинаковые темы у разных писем — обычное дело: «0000-0728699, ООО ТК Зелёная
Русь-исправить ЗП» может встречаться в таблице дважды, и это ДВЕ разные переписки.
Поиск по теме и номеру возвращает письма обеих, поэтому сохранённый при добавлении
id ветки используется как **ориентир внутри результатов поиска**: из ответа берётся
именно та переписка, чей id записан в строке.

Так работают и кнопка 🏷️, и «Выполнено», и карточка в панели. Если сохранённого id
нет (строку добавили до появления колонки), выбор идёт как раньше — по теме, номеру
и близости даты.

## Кнопка «Выполнено» и любое письмо ветки

В колонке «ID письма» лежат id тех писем, что были видны в момент добавления, — ответ,
пришедший позже, туда не попадал, и кнопка на нём свою строку не находила. Теперь при
нажатии берётся id **всей переписки** открытого письма и строка ищется по пересечению
с колонкой: кнопка срабатывает на любом письме ветки и не путает строки с одинаковой
темой.

Форма Alt+Y тоже записывает id открытого письма (и писем раскрытой ветки) — раньше id
появлялся только при перетаскивании.

## Как работает кнопка 🏷️ (синхронизация метки)

Прогон идёт в две фазы:

1. **Находим переписку каждой строки.** Сначала по сохранённым id письма (колонка
   «ID письма»), но только по тем, которые реально существуют в этом ящике; иначе —
   поиском по теме и номеру.
2. **Одна переписка — одно решение.** Разные строки часто указывают на одну и ту же
   переписку (одинаковая тема или один номер ЗП). Если одна из них выполнена, а другая
   нет, раньше строки затирали работу друг друга: одна ставила метку, другая её тут же
   снимала. Теперь на ветку принимается одно решение, и «поставить» побеждает «снять».

Результат каждой операции **проверяется по факту**: почта отвечает «ок» и на id,
которых у неё нет (например, снятых в чужом ящике), молча ничего не делая — из-за
этого отчёт мог рапортовать «поставлено 6», хотя метку получили два письма. Теперь
непроставившиеся считаются отдельно: «не применилось N».

Подробности прогона пишутся в консоль почты одной строкой
`[Проблемные письма] Синхронизация метки «…»` — там по каждой ветке видно тему,
строки таблицы, использованные id, ответ почты и фактический результат.

## Поиск письма по папкам

Письмо ищется по папкам в порядке: Входящие → пользовательские → Отправленные
(в «Отправленных» лежат копии, поэтому они последние). Папка считается подходящей,
только если в её ответе нашлась **именно нужная ветка** — если просто «нашлись
какие-то письма по запросу», перебор продолжается. Иначе чужая переписка со
случайным совпадением обрывала поиск, нужная ветка в другой папке не находилась, и
метки ставились через одну. Если ни одна папка не подошла — делается обычный
глобальный поиск, а если фильтр папок в этой сборке почты не работает, постадийный
поиск отключается сам.

## Тема, текст письма и поиск переписки

Тема и текст письма — **разные** поля. Если тащить не всю ветку, а письмо из неё,
узла темы в строке нет и тема берётся из `aria-label`, где почта диктует
«отправитель, тема, начало текста, дата». Начало текста вырезается по позиции: всё,
что идёт после него, к теме не относится.

Само начало текста при этом не выбрасывается, а сохраняется в отдельную колонку
**«Текст письма (начало)»** — это вторая примета переписки помимо темы. Она нужна
там, где темы не хватает:

- письмо **без темы** («(Без темы)») теперь можно найти вообще — поиск идёт по началу
  текста, раньше запрос был пустым и переписка не находилась;
- когда под одну тему подходит **несколько разных переписок** (типовые «перемещение —
  таборы» от одного склада), остаётся та, где начало текста совпало с сохранённым.

Сравнение идёт по префиксу: в списке почта обрезает превью по ширине колонки, а в
ответе web-api длина своя — совпадать целиком они не обязаны.

Колонка выключена по умолчанию (как и «ID письма») — включите её в Настройках,
выделив свободный столбец таблицы.

### «Re:» — не часть темы

`Re:`, `Fwd:` и их русские варианты вырезаются из темы: и при добавлении в таблицу,
и при построении поискового запроса. Почта лепит их и в начало, и в конец
(«Re: Юдилен-холод Re:»), причём в строке ВЕТКИ и в строке отдельного письма
по-разному — из-за этого одна и та же переписка попадала в таблицу под двумя разными
темами, а поиск по теме с «Re:» терял часть писем. Если тема состояла только из
пометок, она остаётся как была — пустая тема хуже.

### Когда честнее ответить «письма нет»

Порядок отбора ветки: **тема → начало текста → номер**. Номер идёт последним не зря:
один номер ЗП стоит в темах десятка разных писем.

Если в строке есть И тема, И начало текста, и **ни одно из них** не совпало ни с
одним найденным письмом — расширение отвечает «не найдено» и на этом останавливается.
Раньше оно шло дальше и брало ветку по номеру в теме, считая такое совпадение
надёжным. Из-за этого письмо, добавленное коллегой в её ящике (которого в вашем
попросту нет), «находилось» как совсем другая переписка с тем же номером ЗП, и метка
уходила на неё.

Совпадение по номеру теперь считается надёжным, только когда сверять было не с чем —
темы в строке нет. Если тема есть, но не совпала, такую ветку принимаем лишь при
близкой дате (±4 дня).

### Сохранённый id — ещё не доказательство

Когда поиск не нашёл письмо, остаётся последняя попытка — спросить почту по
сохранённым id. Но id у каждого ящика **свои** и идут подряд, поэтому чужой id вполне
может существовать и здесь, указывая на совершенно другое письмо. Поэтому найденное
по id письмо дополнительно сверяется с приметами строки: временем письма (`ts:` —
оно одинаково во всех ящиках), темой и началом текста. Не сошлось — id отбрасывается.

## Когда письма нет в этой почте

Строку, для которой поиск честно ответил «письма в этом ящике нет», видно сразу:

- кружок слева от темы **красный, с крестиком** (вместо числа писем);
- в карточке — «❌ Не найдено»;
- клик по теме **не запускает поиск** в почте, а просто говорит, что искать нечего.

Прежний (возможно, ошибочный) результат при этом **выбрасывается** из кэша. Раньше
его оставляли, и карточка продолжала показывать чужое тело и чужого автора, найденных
старой, менее строгой версией поиска, — хотя новый поиск это письмо уже отверг.

Запасной поиск по разметке открытого списка тоже стал строгим: тема строки таблицы
должна совпасть с **темой строки списка** (а не «встретиться где-то в её тексте»), и
если известно начало текста письма — оно тоже должно совпасть. Раньше при отсутствии
узла темы за тему принимался весь текст строки (отправитель + метки + тело), и в
карточку попадало случайное письмо.

## Сортировка и фильтр: применяются сразу и запоминаются

Смена сортировки не перерисовывала список: подпись, по которой панель решает «менялось
ли что-нибудь», учитывала фильтр и поиск, но **не сортировку**. Выбор как будто не
применялся, пока список не менялся сам по себе, — приходилось закрывать панель и
открывать заново. Теперь сортировка в подписи есть.

Сортировка и выбранный склад **запоминаются** в браузере сотрудника (у каждого свои):
раньше при каждой загрузке почты снова вставало «Сначала старые». Если сохранённого
склада в таблице больше нет (письма по нему закрыли), фильтр честно сбрасывается —
иначе в выпадающем стояло бы «Все склады», а список был бы отфильтрован в пустоту.

## Кнопка «Выполнено» в раскладке «письмо справа от списка»

Кнопка требовала id письма **из адреса** (`#/message/…`). В раскладке, где письмо
открывается правой панелью, адрес остаётся на папке или метке — id взять неоткуда, и
кнопка не появлялась вовсе, хотя письмо открыто и метка на нём есть.

Теперь id ищется ещё и в разметке открытого письма, а показывается кнопка по тому же
признаку, по которому и работает нажатие: есть **id или тема** открытого письма.

Заодно в этой раскладке адрес не меняется при переходе между письмами, поэтому смену
письма по нему не увидеть. Признаком считается клик: после него кнопка десять секунд
опрашивает разметку часто, как при обычной смене адреса.


## Кнопка «Выполнено»

Появляется на открытом письме, если на нём висит одна из ваших меток. По умолчанию
стоит под стопкой плашек, но её можно **перетащить мышью** в любое место экрана —
положение сохраняется в локальном хранилище браузера, то есть только у вас: коллегам
кнопка никуда не переезжает. Двойной клик возвращает её под плашки. Если кнопку не
трогали, она остаётся там же, где была.

Цвет кнопки, цвет текста и непрозрачность задаются в Настройках,
отдельным блоком «✅ Кнопка «Выполнено»» — так же, как у плашек меток.

Возврата «на место» по двойному клику нет намеренно: двойной клик — это два обычных
клика, и первый же отмечал письмо выполненным. Нужно другое место — перетащите кнопку.

## Оформление таблицы не затирается

Строка добавляется **в первую свободную строку листа**, без структурных изменений:
Values API меняет только значения ячеек и не трогает заливку, рамки, форматы и
чекбоксы. Раньше перед записью всегда вставлялась новая строка (`insertDimension`) —
она приходила с форматом соседней сверху, а всё, что ниже, сдвигалось, и наведённое
в таблице оформление разъезжалось. Вставка строки осталась только на случай, когда
свободных строк на листе действительно не осталось.

## Обновление меток: по одной или все сразу

Кнопка **🏷️** на плашке синхронизирует свою метку: ставит её на невыполненные письма
этой плашки и снимает со всех остальных строк таблицы.

Когда плашек больше одной, над стопкой появляется горизонтальная полоса
**«🏷️ Обновить метки»**: одно подтверждение и один общий итог вместо нескольких
одинаковых. Пока идёт прогон, на ней виден счётчик `2/3`.

Полоса появляется, только когда обновления ждут **две и больше** плашек: для одной
хватает её собственной красной 🏷️, а полоса рядом была бы вторым способом нажать то
же самое. Обновляются при этом **только те плашки, в которых состав писем изменился**: гонять все семь, когда поменялась одна, — лишние минуты и лишние запросы
к почте. Если таких плашек несколько, их число видно прямо на полосе, а имена — в
подсказке и в подтверждении.

### Видно, что сейчас обновляется

Раньше о ходе прогона говорило только «кнопка нажата»: на большой плашке казалось, что
расширение зависло, а какая из плашек сейчас работает — было не видно вовсе.

Теперь состояние показывается там, где его ищут глазами:

- **все ждущие плашки** сразу помечаются часиками — очередь видна с самого начала;
- **работающая плашка** крутит часики; закончив, освобождается и уступает следующей;
- **строки внутри неё** крутят часики прямо в кружке слева от темы. Обработалась
  строка — её кружок сразу освобождается, и с ней можно работать, не дожидаясь
  остальных. Пропущенные («метка уже стоит») не мигают вовсе: они и так готовы.

Порядок — **от самой маленькой плашки к самой большой**: маленькая отрабатывает первой
и сразу перестаёт держать внимание. Плашки идут строго **по одной**: раньше их пускали
по две параллельно — быстрее на пару секунд, но часики горели сразу на нескольких, и
понять, что происходит, было нельзя. Прогон теперь занимает секунды, так что ясная
картинка важнее выигрыша.

Если прогон оборвался, часики снимаются со всех плашек и строк, до которых не дошли.
Тем, у кого в системе отключена анимация, часики показываются статично — смысл тот же.

### Как идёт синхронизация и сколько это стоит

Порядок работы кнопки 🏷️:

1. **Один** запрос «какие письма сейчас носят эту метку».
2. По нему сразу отсеиваются строки, которые заведомо ни при чём: строка чужой
   плашки нужна только чтобы **снять** метку, а снимать нечего, если её там нет.
   Совпадение проверяется по сохранённым id, времени письма и теме — без запросов.
3. Оставшиеся строки разбираются пачками по 5: поиск письма + выборка всех писем
   ветки по её `tid`.
4. Одинаковые переписки из разных строк сводятся в одну — одно решение на ветку,
   «поставить» побеждает «снять».
5. `do-label` / `do-unlabel` на ветку.
6. **Один** запрос «кто носит метку теперь» — им сразу проверяются все ветки
   (почта отвечает «ок» и на чужие id, ничего не делая) и находятся «хвосты»:
   письма с меткой, которых в таблице нет.

**Строку, где метка уже стоит на ВСЕЙ ветке, не трогаем вообще.** Это проверяется без единого
запроса — по выборке из пункта 1: совпали сохранённые id, либо время письма вместе с
темой. Раньше такой проверки не было (была только зеркальная — «снимать нечего, если
метки нет»), и каждый прогон переставлял метку на **все** письма плашки заново. Отчёт
при этом бодро писал «поставлено 86», хотя 85 из них уже были помечены. Теперь в
отчёте отдельная графа: «поставлено 1, уже стояло 85».

Если метка стоит на ветке **частично** — например, пришёл новый ответ и он без
метки, — строка не пропускается: часть сохранённых id не нашлась в выборке «кто носит
метку», значит ветку надо дописать. Пропуск срабатывает только когда помечены все
письма ветки, которые расширение знает.

**Плашки обновляются параллельно, по две за раз.** Закончившая сразу перестаёт быть
красной и снова готова к работе — ждать остальные не нужно. Больше двух одновременно
не запускаем: внутри каждой уже пять параллельных запросов, и почта начнёт
придерживать ответы. **«Хвосты»** — письма, на которых метка висит, а в таблице их нет — прогон не
задерживают. Снимать с них метку некритично, поэтому вместо модального окна посреди
работы после отчёта показывается тост «Ещё N писем с меткой … нет в таблице» с
кнопкой **«Снять метки»**: нажмёте — снимется фоном, не нажмёте — предложим в
следующий раз. Один тост на все плашки сразу.

Проверка «хвостов» идёт и тогда, когда разбирать нечего (всё уже проставлено): письмо
могло получить метку мимо таблицы — руками в почте или из удалённой строки.

Замеры (запросов к почте):

| | было | стало |
|---|---|---|
| Плашка «Архив»: 85 писем помечены, добавилось одно | 260 | **5** |
| Таблица 40 строк, у плашки свои две | 73 | **14** |
| Загрузка почты с закрытой панелью | 40 | **0** |

- разбирались **все** строки таблицы, хотя большинству метка не нужна;
- проверка «метка правда легла?» стоила отдельного запроса **на каждую ветку** —
  теперь одна выборка на весь прогон, она же идёт на поиск «хвостов»;
- форма запроса к почте (их несколько вариантов под разные сборки) подбиралась
  заново при каждом вызове — теперь сработавшая запоминается на сессию;
- поиск письма для карточек шёл даже при **закрытой** панели: на загрузке почты это
  был запрос на каждую строку таблицы впустую. Счётчики на плашках считаются по
  таблице и в этих запросах не нуждаются.

### Письмо, которого нет в этом ящике, метится красным из ЛЮБОГО пути

Красный кружок с крестиком ставил только один путь — обновление карточек панели.
А прогон меток, выяснив ровно то же («письма в этом ящике нет»), писал в отчёт
«писем не найдено 1» и на этом останавливался: найти эту строку в панели было нельзя,
потому что красным её никто не пометил, а до неё обновление карточек могло и не дойти.

Теперь строку метит и прогон меток, и в консоль выводится её номер и тема — «не найдено
1» без указания, какого именно письма, искать не помогает.

### Плашки, которые в прогон не вошли, названы прямо

Полоса «Обновить метки» гоняет только те плашки, где **состав строк изменился**. Это
экономит время, но арифметика переставала сходиться: в плашках 98 писем, а в отчёте
«поставлено 96» — и непонятно, куда делись остальные.

Теперь отчёт называет пропущенные плашки и причину. Отдельно оговаривается случай, из-за
которого расхождение чаще всего и возникает: **метки сняли вручную в самой почте**.
Состав строк в таблице при этом не менялся, расширение об этом знать не может и плашку
не трогает — надо нажать 🏷️ на ней самой, она работает всегда.

### Красный — значит метки устарели

Работая в одиночку, видно: сколько строк в таблице — столько писем с меткой в почте.
Вдвоём (или на следующий день) таблица уже другая, а метки в **вашей** почте прежние,
и понять это, не нажав 🏷️, было нельзя.

Поэтому после каждой удачной синхронизации панель запоминает состав строк плашки.
Пока он тот же — всё спокойно. Изменился (коллега добавила письмо или закрыла своё) —
кнопка 🏷️ этой плашки краснеет и появляется полоса «Обновить метки».

**Свои действия красным не подсвечиваются.** Когда письмо перетащили вы, отметили
«Выполнено» или отменили отметку, расширение тут же само поставило или сняло метку —
обновлять нечего. Такие изменения помечаются как свои и при следующей загрузке строк
просто перезаписывают слепок.

Слепок хранится в локальном хранилище браузера: он про вашу почту, у сменщицы своя
картина.

Если слепка **ещё нет** — плашку только что завели или расширение поставили недавно, —
значит метки этой плашки в вашей почте не проставляли ни разу. Тогда: писем в плашке
нет — молчим (синхронизировать нечего); письма есть — красное. Одно нажатие 🏷️, и
плашка успокаивается.

## Строки, добавленные сменщицей, больше не разбираются заново

Пропуск «метка уже стоит на всей ветке — не трогаем» держится на приметах строки:
сохранённых id письма **или** связке время письма + тема. Но проверка «а на всех ли
письмах ветки метка?» сверяла **все** сохранённые id с выборкой «кто носит метку».

Идентификаторы писем выдаёт почтовый ящик: строка, которую завела сменщица, хранит id
**её** ящика, и в вашей выборке они не найдутся никогда — сколько бы меток ни стояло.
Проверка честно отвечала «часть ветки без метки», пропуск гасился, и строка шла в
полный разбор (поиск письма + выборка ветки, два запроса) при **каждом** прогоне.
Отсюда и «80 писем обновляются минутами»: чем больше строк завела сменщица, тем меньше
работал пропуск — вплоть до полного отключения, если все строки чужие.

Теперь на «не всё помечено» проверяются только **свои** id — те, что реально нашлись в
этом ящике. Ветка, опознанная по времени письма и теме (они одинаковы во всех ящиках),
пропускается как помеченная. Защита от «пришёл новый ответ без метки» при этом
сохраняется для строк, добавленных в вашем ящике, — там id свои и сверять их есть с чем.

Для строки сменщицы сверять по id нечего, поэтому полнота проверяется иначе — **по
числу писем в ветке**: карточка панели его показывает и держит в кэше. Помечено меньше,
чем писем в переписке, — значит пришёл новый ответ без метки, и строка разбирается.
Запросов к почте это не стоит: берётся то, что и так лежит в памяти. Если размер ветки
ещё неизвестен (панель эту строку не открывала), строка пропускается — новый ответ
получит метку на следующем прогоне, когда карточка обновится.

## От чего зависит вся экономия: выборка «кто носит метку»

Прогон 🏷️ начинается с **одного** запроса «какие письма сейчас носят эту метку». На нём
держится всё: по нему отсеиваются строки соседних плашек (снимать нечего, если метки
там нет) и пропускаются свои строки, где метка уже стоит. Не получили выборку —
расширение честно идёт по ветке «спросить не удалось» и разбирает **каждую** строку
таблицы: два запроса к почте на строку, минуты вместо секунд.

Ответ принимается, только если почта вернула письма, **действительно** носящие метку.
Проверка обязательна: если фильтр `lid` не сработал и вернулся весь ящик, принять такой
ответ — значит счесть помеченными все письма подряд, и метки не проставятся вообще.

Вся проверка упирается в разбор поля меток письма, а форма ответа у разных сборок почты
разная. Раньше разбирались только `labels` массивом и `lid` массивом; **карта**
`lid→{…}` не разбиралась вовсе — ветка для объекта смотрела `lid` у самого поля, а
`typeof {} === 'object'` уводил одиночное значение мимо. Не разобрали метки — ни одна
форма запроса не подтверждалась, выборка отвергалась целиком, и экономия отключалась.

Теперь поддерживаются `labels`, `label`, `lid`, `labelIds`, `label_ids` — массивом строк,
массивом объектов `{lid}`, картой `lid→{…}` и одиночным значением.

### Форма запроса подсматривается у самой почты

Как именно эта сборка просит «покажи письма с меткой», заранее неизвестно: модель
`messages` по `tid` отвечает, а по `lid` в некоторых сборках молчит — возвращает ответ
вообще без данных, и перебирать написания фильтра можно долго.

Но когда открыт вид метки (`#/label/<lid>`), почта запрашивает ровно это **сама**.
`inject.js` уже перехватывает её запросы ради «конверта» — заодно он запоминает
параметры модели `messages` из последнего настоящего запроса. Панель берёт написание
фильтра оттуда и ставит эту форму первой в очередь; перебор остаётся лишь на случай,
когда подсмотреть нечего (в метку ни разу не заходили).

Сработавшая форма запоминается **шаблоном**: на месте идентификатора метки стоит
заполнитель, который подставляется перед каждым запросом. Иначе вторая плашка спросила
бы письма первой — id метки у каждой свой, а форма помнится одна на сессию.

Если ни одна форма не подошла дважды подряд, расширение перестаёт пробовать до
перезагрузки страницы: восемь заведомо пустых запросов на каждую плашку при каждом
прогоне стоят дороже, чем ещё одна попытка. Тот же приём, что для поиска по папкам
(`fid`) и выборки по `tid`.

### Выборка читается постранично

Метка висит на **ветках целиком**, а не на отдельных письмах: у 86 строк таблицы легко
набирается 400–500 помеченных писем. Один запрос отдаёт максимум 200, и выборка
обрывалась на первой странице. Последствий было два, и оба выглядели как поломка:

- строки, чьи письма не попали в первые 200, считались непомеченными и разбирались
  заново — то есть экономия работала только на части таблицы;
- проверка «легла ли метка» идёт по такой же выборке, поэтому письма за границей 200
  попадали в отчёт как **«не применилось»**, хотя на самом деле были помечены.

Теперь страницы дочитываются, пока почта их отдаёт (до 2400 писем на плашку). Сколько
страниц ушло, видно в разборе прогона.

### Обходной путь, если метки на письмах не читаются

Но перебрать все формы поля меток заранее нельзя, поэтому есть и обходной путь. Если
метки на письмах не прочитались **вообще** (не «часть писем чужие», а «поле в незнакомом
виде»), проверяется сам фильтр: тем же запросом спрашивается заведомо несуществующая
метка. Пусто в ответ — фильтр `lid` почта уважает, значит в основном ответе лежит именно
множество этой метки, читается поле меток или нет, и выборку можно принять. Вернулись
письма — фильтр игнорируется, ответу верить нельзя. Проба стоит один запрос на сессию.

Если и это не помогло, в консоли почты появляется предупреждение с разбором по каждой
опробованной форме запроса: сколько писем вернулось, у скольких нашлась нужная метка,
какие поля пришли у письма и что из них удалось прочитать как метки. Печатается текстом,
а не объектом: объект консоль сворачивает, и при копировании от него остаётся `[{…}]`.

## Почему пропуск мог не сработать: диагностика прогона

Пропуск «метка уже стоит — не трогаем» держится на приметах письма из ответа почты:
**времени** и **теме**. Формы ответа у разных моделей и сборок почты разные — у поиска
тема приходит строкой, а выборка по метке в части сборок отдаёт её объектом или под
другим именем. Пустая тема здесь стоит дорого: без неё не опознаётся ни одна строка,
добавленная в чужом ящике, и прогон снова разбирает всё подряд.

Поэтому тема и время из ответа разбираются устойчиво (`subject` строкой и объектом,
`subjText`, `utc_timestamp`, `receive_date`), а сам прогон **всегда** печатает в консоль
почты одну строку с разбором:

```
[Проблемные письма] Синхронизация «⁉️Архив»: разбираем 87 строк из 125
  писем с меткой в почте: 87
  из них со временем: 87
  из них с темой: 0          ← вот здесь пропуск и рвётся
  поля ответа почты: [mid, tid, subjText, …]
  своих строк: 87
  у них сохранены id: 87
  опознано по id: 0
  пропущено (метка уже стоит): 0
```

Рядом печатается пример первой строки, которую **не** пропустили: её тема, содержимое
колонки «ID письма», разобранные из неё id и время. По этим двум строчкам видно, чего
именно не хватило, — без включения отладки и повторного прогона.

## Полнота метки считается по ВЕТКЕ, а не по окну времени

Строку, заведённую в чужом ящике, расширение опознаёт по времени письма и теме.
Но совпадение по времени берёт только письма в пределах 12 часов от сохранённого,
а переписка тянется днями: у ветки из восьми писем в окно попадает одно.

Проверка «а вся ли ветка помечена?» сравнивала именно это одно письмо с размером
переписки — всегда получала «1 из 8» и гасила пропуск почти на каждой строке коллеги.
Прогон снова разбирал 94 строки из 125, хотя метки давно стояли, и в отчёте бодро
писалось «поставлено 57» на письма, помеченные ещё вчера.

Настоящую группировку даёт `tid`. Теперь по нему собирается **вся помеченная часть
ветки** — без единого запроса, из той же выборки, — и сравнивается с числом писем
переписки из карточки. Её письма заодно попадают в «известные»: раньше те из них, что
не попали в 12-часовое окно, потом считались «хвостами» и предлагались к снятию метки.

## Чей ящик выдал id — пишем прямо в колонку

Рядом с временем (`ts:`) в колонку «ID письма» пишется `u:<ящик>` — чей ящик выдал эти
идентификаторы. Время говорит «какое письмо», владелец — «чьи это id».

Идентификаторы писем у каждого сотрудника свои, поэтому проверять чужие в своей почте
бессмысленно: запрос уйдёт, а ответ либо пуст, либо указывает на постороннее письмо.
Раньше это выяснялось только по факту — запросами. Теперь строка сменщицы видна сразу:
её id не подставляются ориентиром в поиск и по ним не спрашивается почта, ветка ищется
по теме, началу текста и времени. Строки без пометки (заведённые раньше) работают
как прежде.

## На что именно ставится метка

Метка ставится не «на ветку» одной командой, а на **список писем**: расширение
перечисляет почте id всех писем переписки. Значит всё упирается в полноту этого списка.

Список собирается выборкой писем по `tid` — настоящей группировке почты. Если такая
выборка в сборке не работает, расширение молча откатывается к тому, что вернул **поиск**,
а поиск возвращает лишь письма, совпавшие с запросом. Метку тогда получает часть
переписки, а новые ответы — нет. Выглядит это как «метка не доставляется», и раньше
никакого следа в консоли не оставляло.

Теперь:

- форма запроса «дай все письма этой переписки» **подсматривается у самой почты** —
  ровно так же, как форма запроса писем метки. Когда человек открывает письмо, почта
  делает такой запрос сама; расширение берёт написание оттуда и ставит его первым в
  очередь, а перебор остаётся подстраховкой;
- если выборка по ветке всё-таки не работает, об этом пишется прямо, с подсказкой
  открыть любое письмо, чтобы форму можно было подсмотреть;
- после каждого прогона видно, сколько веток помечено по **полной** выборке, а сколько
  по неполной, и почему — **без id переписки** (поиск его не вернул, спрашивать письма
  не у чего) или **выборка не удалась** (id есть, но ответа нет). Причины разные и
  лечатся по-разному, поэтому считаются отдельно; совет «откройте письмо» показывается
  только пока форма запроса ещё не подсмотрена.

## Полноту метки не вычисляем, а спрашиваем

Все попытки понять «вся ли ветка помечена» из чисел проваливались одинаково, и каждая
выглядела убедительно, пока не встречала живую переписку:

- `count` в ответе «письма с меткой» считает только письма, попавшие **в фильтр**, то
  есть уже помеченные;
- число писем из карточки панели считается **по поиску**, а поиск возвращает лишь
  совпавшие с запросом.

На переписке из 25 писем, где метку носят 22, оба источника говорят «22 из 22». Строка
пропускается как готовая, и три письма остаются без метки — сколько ни жми «Обновить».

Поэтому полноту больше **не вычисляем**. Если ветка узналась в выборке, мы знаем её
`tid` — и просто спрашиваем её у почты: один запрос, точный список писем, сверка с теми,
на которых метка стоит. Ничего не не хватает — строку не трогаем. Не хватает — метим
**всю ветку** сразу, без поиска письма.

Строке, которой нужна дописка, это обходится даже **дешевле** прежнего пути: был поиск,
затем выборка ветки, затем простановка (3 запроса) — стало выборка и простановка (2).
Уже готовой строке — один запрос вместо нуля; это цена за то, что ответ верный, а не
правдоподобный.

В разборе прогона появилась строка «сверено запросом к переписке» — сколько строк
проверено точно, а не по догадке.

## Новое письмо в помеченной ветке метку получает

Пропуск «метка уже стоит — не трогаем» сравнивает число помеченных писем ветки с её
**настоящим размером**. Размер берётся из кэша карточки панели: он считается по поиску,
который меткой не ограничен.

Поле `count` из ответа «письма с меткой» для этого **не годится**, хотя и выглядит
подходящим. Ответ отфильтрован по метке, и `count` считает только письма, попавшие в
фильтр, то есть уже помеченные. Приняв его за размер ветки, проверка превращается в
тавтологию: «помечено 15 из 15, пропускаем» — при том, что в переписке 20 писем и пять
из них без метки. Именно так метка переставала доходить до новых ответов, а отчёт
показывал «уже стояло» и был по-своему прав.

Если размер выяснить не удалось, строка **не** пропускается. Раньше было наоборот, и это
ломало главное: в помеченную ветку приходит новый ответ, размер ветки неизвестен, строка
пропускается — и ответ остаётся без метки насовсем. Пропуск ценен ровно тогда, когда мы
уверены, что дописывать нечего; уверенности нет — дешевле разобрать строку, чем потерять
метку на новом письме.

## «Обновить метки» обновляет ВСЕ плашки

Раньше полоса брала только те плашки, где изменился состав строк таблицы, и появлялась
только при таких изменениях. Экономия имела смысл, пока плашка обновлялась минуты; теперь
уже проставленная стоит пары запросов и доли секунды.

А цена у пропуска была высокая. Расширение видит изменения **в таблице** и не видит, что
метку сняли **руками в самой почте**: состав строк тот же, плашка не краснеет, прогон её
не берёт — и «обновить всё» молча обновляло не всё, догонять приходилось поштучно.

Теперь:

- полоса доступна **всегда**, когда плашек больше одной, и обновляет их все;
- красный цвет остался подсказкой «в таблице что-то менялось», число в скобках — сколько
  таких плашек. Нажать можно в любой момент, независимо от цвета;
- обычный (некрасный) вид полосы настраивается: Настройки → «🏷️ Полоса «Обновить метки»»
  — цвет, цвет текста, непрозрачность. Красное состояние настройкой не перебивается:
  красный здесь сигнал, а не оформление.

## Перерисовка списка не выбрасывает из письма и из поиска

Метки, поставленные через API, Яндекс в уже отрисованном списке не показывает, поэтому
после простановки список перерисовывался — **кликом по текущей папке в боковом меню**.
Клик по папке уводит почту в список этой папки. Если человек в этот момент читал
открытое письмо, оно закрывалось само собой через несколько секунд (уборка «хвостов»
идёт фоном уже после отчёта). Если на экране были результаты поиска — они сменялись
списком папки, и поиск выглядел неудачным.

Теперь клик по папке не делается, когда:

* открыто письмо или ветка (`#/message/…`, `#/thread/…`);
* показаны результаты поиска (`#/search?…`);
* панель сама только что повела к письму — 15 секунд после этого.

Кнопка «проверить новые письма» нажимается в любом случае: она обновляет список и
никуда не уводит.

## Крошки печатаются сразу, а не только после перезагрузки

Первая версия журнала писала шаги только в хранилище, а печатала их при следующей
загрузке страницы. Но письмо закрывается **без** перезагрузки — и смотреть в консоль
после этого было не на что: крошки лежали в хранилище и ждали события, которого не
происходило. Теперь каждый шаг печатается сразу, строкой с меткой `⟐`, а хранилище
остаётся страховкой на случай, если страница всё-таки перезагрузится.

Под запись попали **все синтетические клики** панели — самое вероятное объяснение
«письмо закрылось само»: кнопка «проверить новые письма», клик по папке (по активной и
по папке ветки), разворот ветки в списке, снятие чипа фильтра поиска. Каждый называет
элемент, по которому кликнул: тег, классы, `aria-label`, текст.

И отдельно — наблюдатель за открытым письмом: раз в секунду смотрит, какое письмо
открыто, и отмечает сам момент закрытия. Он нужен потому, что в раскладке «список
слева, письмо справа» письмо закрывается **без смены адреса**, то есть по `hashchange`
этот момент не поймать. Теперь в журнале видно, что панель делала за секунду до
закрытия — и делала ли вообще.

## Хлебные крошки: что было перед перезагрузкой вкладки

Три круга подряд диагноз упирался в одно: «письмо закрылось, а в консоли пусто».
Оказалось, пусто именно потому, что **вкладка перезагружалась** — а перезагрузка чистит
консоль вместе со всеми строками, которые мы напечатали секундой раньше. Проверять
следы по консоли в такой ситуации бессмысленно по построению.

Поэтому важные шаги пишутся ещё и в `chrome.storage.local` (`pm_trace`, последние 40
записей): смена адреса — и кем она сделана, клик по папке, запуск поиска, фоновая
уборка «хвостов», отмена шага, выгрузка страницы. На старте панель печатает эту дорожку
с относительным временем:

```
Что делала панель перед прошлой выгрузкой вкладки (последнее — внизу):
  −4.2 с  поиск письма в почте (Юдилен-холод)   адрес: #/folder/17
  −1.1 с  адрес сменился (это сделали не мы)    адрес: #/message/1939…
  −0.3 с  фоновая уборка хвостов (писем: 3)     адрес: #/message/1939…
  −0.0 с  страница перезагружается или закрывается
```

## Спекулятивные запросы отключали рабочий механизм

В журнале появилось то, чего раньше не было:

```
Выборка писем переписки (tid) не работает в этой сборке — метка ляжет только на письма
из результатов поиска
```

Это неправда: выборка работает, её форма подсмотрена у самой почты. Выключила её
собственная правка. Поиск письма по сохранённому id последним шагом перебирал **все**
сохранённые id как id ветки — «а вдруг это ветка». Для обычных id письма такой запрос
закономерно ничего не возвращает, но каждая неудача засчитывалась как отказ самого
механизма, и после **двух** он отключался на весь сеанс. Панель проходит по трёмстам
строкам, так что двух неудач набиралось на первых же секундах.

Дальше рушилось всё, что на этом механизме держится: точный поиск письма по id и
простановка метки на всю ветку. То есть переход к письму работал хуже, чем до правок, —
и ровно поэтому.

Спекулятивного перебора больше нет: выборка веток зовётся только для id, которые
записаны **как ветка** (с префиксом `t`). Плюс порог отказа поднят с 2 до 5: пары строк
с устаревшим id (письмо удалили, ветку перенесли) не должно хватать, чтобы выключить
рабочий механизм.

## id для перехода берётся ИЗ ТАБЛИЦЫ

Предыдущая версия этой правки не работала вовсе. Она брала id письма из результата
поиска (`cachedInfo`), а когда карточка построена из видимого списка писем, полей с id
там просто нет — условие «есть id, открываем напрямую» не выполнялось ни разу, и всё
шло прежним путём по теме.

Настоящий id лежит в колонке «ID письма». Раньше его сюда сознательно не подставляли:
«id сняты из ящика того, кто добавлял письмо, а у каждого сотрудника свои». Это верно,
но теперь колонка помечена владельцем (`u:<uid>`), и своё от чужого отличается точно.
Берём строго: только когда владелец колонки — этот самый ящик. Строки коллеги и старые
строки без пометки идут прежним путём.

## Переход к письму идёт по id, а не по теме

Клик по теме в панели работал так: искать письмо в видимом списке **по теме** → не нашли
→ перейти в папку ветки → не нашли → искать по теме в почте. Для повторяющихся тем это
давало два разных промаха:

* **в своей папке** находилось *первое совпадение по теме* — то есть соседнее письмо с
  такой же темой;
* **в чужой папке** запускался глобальный поиск: «Перемещение Королёв Стан -Борисов» даёт
  три сотни результатов, нужного среди отрисованных нет, и появлялось «Ветка не найдена
  в списке».

И то, и другое — мимо, при том что точный id письма записан в строке таблицы.

Теперь порядок такой:

1. ищем в списке **строго по id письма строки** (а не по теме);
2. не нашли, но id известен — **открываем письмо напрямую** по его адресу;
3. поиск по теме остаётся только для строк без сохранённого id.

## Переход к письму по-прежнему ищет письмо, а не подменяет поиск открытием

Была попытка сделать последним шагом перехода «не нашли в списке — открываем само письмо
по id». Это не то, что нужно: переход по теме должен **показать письмо в списке**, а не
увести в отдельное письмо. Попытка убрана, порядок прежний: список → папка ветки →
поиск почты.

Что от неё осталось полезного — поиск в списке идёт **строго по id письма строки**, а не
по теме: раньше в своей папке находилось первое письмо с такой же темой.

Заодно: один и тот же поиск, запущенный повторно в пределах 2,5 секунды, не
перезапускается. В журнале это выглядело как семь одинаковых строк «поиск письма в
почте» подряд — повторные клики и наложение отложенных шагов.

## Карточка сначала строится из ВИДИМОГО списка писем — и там была та же ошибка

Долгий поиск причины «в карточке не то письмо» упирался в то, что в консоли не было ни
одной строки про эту строку таблицы — ни успеха запроса по id, ни неудачи. Объяснение
оказалось простым: **до запроса к почте дело и не доходило.**

Карточка собирается в три захода: кэш → **видимый список писем на экране** → и только
потом запрос к почте. Второй заход ищет письмо в списке по теме и началу текста — и
сравнивал начало текста по первым **сорока** символам. Ровно та же ошибка, что раньше
нашлась в сверке через почту, но в другом месте кода: письма по шаблону («Доброй ночи.
Водитель прибыл на загрузку …») совпадают этими сорока символами дословно. Проходили
оба письма, а список отсортирован по дате — и бралось самое свежее.

Починено обоими способами сразу:

* начало текста сравнивается **целиком** (до 200 символов), а не по сорока;
* если у строки сохранён id письма, из списка берётся строка **с этим id**, а не первая
  подходящая по теме.

## В карточке — письмо строки, а не самое свежее письмо ветки

Карточка всегда показывала **последнее** письмо ветки. Пока темы уникальны, это незаметно.
Но когда одна и та же тема приходит каждую ночь, выходило так: в таблице письмо от 29.08
со своим текстом, а в карточке — письмо от 05.09 с другим текстом и другой датой. Понять
по экрану, одна это переписка или разные, было невозможно, и выглядело как «поиск нашёл
не то письмо».

Теперь: если в строке записан id **конкретного письма** (а не только id ветки), карточка
показывает именно его — его дату, текст и автора.

Важная тонкость, на которой первая версия этой правки не сработала: у переписки из
**одного** письма id ветки совпадает с id письма — в строке это выглядит как
`t193936258954442575,193936258954442575`, то есть одно и то же число дважды. Попытка
«вычесть id веток из id писем», чтобы не спутать одно с другим, вычитала всё, список
нужных писем оказывался пустым, и карточка снова брала последнее письмо. Вычитать не
нужно вовсе: сверяем сохранённые id только с id **писем** — чистый id ветки просто ни с
чем не совпадёт, и тогда покажется последнее письмо, как и задумано. Человек взял на контроль это письмо,
его и надо видеть. Кнопка «Перейти к последнему письму» рядом остаётся.

Остальные смыслы не тронуты — это важно, чтобы правка ничего не сдвинула:

| Что | Откуда берётся |
|---|---|
| Что показано в карточке | письмо строки (если опознано) |
| Дата письма для таблицы | последнее письмо ветки |
| id для простановки метки | последнее письмо ветки |
| «Перейти к последнему письму» | последнее письмо ветки |

Если в строке только id ветки, письма уже нет в переписке или id нет вовсе — показывается
последнее письмо, как и раньше.

## В таблице храним id ВЕТКИ — единственный запрос, который работает всегда

Диагностика ответила однозначно: на каждой строке подряд —

```
[Проблемные письма] По сохранённому id (193936258954320116) почта письмо не вернула —
придётся искать по теме «…»
```

То есть выборка писем **по id письма** в этой сборке почты не работает ни в одном из
пяти написаний запроса. Поэтому точный путь к письму не включался никогда, и всё всегда
падало в текстовый поиск по теме — со всеми последствиями для писем с повторяющейся
темой.

При этом запрос **«письма переписки» по id ветки работает всегда**: его форму мы
подсматриваем у самой почты (`thread_id`), и она видна в логах.

Поэтому теперь в колонку «ID письма» первым пишется id ветки с префиксом `t`:

```
t193936258954442575,193936258954442575,ts:1787964333000,u:1130000018626852
```

Разбор строки отличает id ветки от id письма, и порядок запросов стал таким:

1. **id ветки** — один точный запрос, работает всегда;
2. id письма — если ветка не записана (старые строки);
3. сохранённый id как id ветки — старые версии писали его без префикса;
4. и только потом поиск по теме.

Старым строкам id ветки дописывается сам: прогон меток теперь дозаполняет не только
время письма, но и id ветки, как только узнаёт его. После одного прогона такие строки
начинают находиться одним запросом.

## После обновления расширения вкладка почты работает со старой копией

Когда расширение обновляют (или выключают-включают) при открытой вкладке почты, скрипт
на странице продолжает жить, но связь с расширением обрывается **навсегда**:
`chrome.runtime` исчезает, и каждый запрос падает с

```
Uncaught TypeError: Cannot read properties of undefined (reading 'sendMessage')
```

Снаружи это выглядит как «сломалось вообще всё»: строк нет, метки не ставятся,
«Не удалось добавить», счётчики по нулям. Лечится одним F5 — но догадаться об этом по
такой ошибке невозможно.

Теперь связь проверяется перед каждым запросом. Потеряна — в панели появляется полоса
«Расширение обновилось. Обновите вкладку почты (F5)», которая никуда не денется (тост
бы исчез, а состояние не временное), плюс запись в консоль и в журнал. Фоновые опросы
при этом останавливаются, чтобы не сыпать ошибками.

**Правило простое: обновил расширение — обнови вкладку почты.**

## «Развернуть ветку» открывало вложения

Кнопка вложений подписана числом («1») и лежит в той же строке письма, что и счётчик
ветки. Отбор шёл по «любому элементу с числом» — и вложения попадались первыми. В
журнале это видно дословно:

```
⟐ разворачиваю ветку в списке (button… .qa-AttachmentsWidgetTotal [Показать все вложения] «1»)
```

То есть вместо разворота ветки раз за разом открывались вложения. Теперь кандидаты с
«вложен»/«attach» в подписи или классе отбрасываются, а если кроме них ничего нет —
не кликаем вовсе.

## Что вернула почта на сохранённый id — печатается в консоль

Когда письмо ищется по сохранённому id, в консоль печатается ответ почты: сколько писем
в ветке, их id, даты и начала текста, и что в итоге показано в карточке. Это
единственное место, где видно, **одна** переписка эти письма или разные: если по id
письма от 29.08 почта отдаёт ещё и письмо от 05.09 — значит для неё это одна ветка, и
карточка показывает её последнее письмо правильно. Если отдаёт одно — причина в другом
месте, и это тоже сразу видно.

## Кэш найденных писем не переживает обновление расширения

В кэше лежат **результаты** поиска письма — то есть выводы той версии, которая их
посчитала. Кэш считается свежим десять минут и восстанавливается из хранилища при
перезагрузке страницы. Поэтому сразу после обновления карточки продолжали показывать
ровно то, что мы только что починили: «обновил, а всё то же».

Теперь рядом с кэшем хранится версия панели. Версия изменилась — кэш выбрасывается, и
письма перечитываются заново. В консоль пишется, что так и задумано.

## Запрос письма по id опирается на форму, подсмотренную у почты

Выборка писем по их id собиралась наугад из трёх написаний. Не подошло ни одно — и
выборка отключалась **на весь сеанс**, а вместе с ней и точный путь к письму: всё
снова шло текстовым поиском по теме.

Теперь первыми пробуются формы, построенные из запроса «письма переписки», который
подсмотрен у самой почты и ей заведомо подходит, — в нём меняется только поле с
идентификатором. И если выборка успела отключиться до того, как форма была подсмотрена,
делается ещё одна попытка уже с ней.

## По сохранённому id спрашиваем почту напрямую, а не ищем по теме

Карточка любой строки строилась **только** текстовым поиском по теме. Сохранённый id
использовался лишь как ориентир ВНУТРИ его результатов — то есть работал, только если
нужное письмо в эти результаты попало.

Для писем с повторяющейся темой это гарантированная ошибка. «Перемещение Королёв Стан
-Борисов» приходит каждую ночь **отдельным письмом и отдельной перепиской**. Поиск
отдаёт свежие, и переписки от 29.08 в его ответе может не быть вовсе — тогда
сохранённому id не с чем совпасть, и карточка показывает соседнюю переписку с той же
темой: другое письмо, другой текст, другая дата. Ровно это и происходило.

Теперь, если в строке есть id этого ящика, письмо спрашивается **у почты напрямую** —
по id письма (а следом подтягивается вся его переписка) или по id ветки, если сохранён
он. Поиск по теме остаётся запасным путём: для строк без id, для строк коллеги и когда
сохранённый id устарел (письмо удалили).

Это ещё и дешевле: один-два точных запроса вместо поиска с перебором папок.

## Со свёрнутой ветки страница отдаёт id ВЕТКИ, а не письма

Перетаскивая свёрнутую ветку, расширение снимает со строки списка идентификатор вида
`t193936258954442575` — это id **переписки**, id письма там нет. Такой id просто
отбрасывался: дата письма не вычислялась и подставлялась **сегодняшняя**, а в колонку
«ID письма» ложился id ветки вместо id писем (по нему потом не работали ни сверка
«метка уже стоит», ни «Выполнено», ни поиск карточки).

Теперь по id ветки спрашиваются её письма — из них берутся и дата, и метки, и
настоящие id.

Заодно то же правило «только та же переписка» распространено на весь результат поиска
по теме, а не только на id: если поиск попал в соседнюю переписку, от неё не берутся ни
дата, ни метки, ни склад. И время письма теперь берётся в первую очередь от самой
ветки, а не от результата поиска: со страницы мы точно знаем, какое письмо перетащили.

## Метка при перетаскивании больше не уходит на соседнюю переписку

При перетаскивании письма расширение брало id из двух источников и **складывало** их:
снятые со строки списка (перетащенное письмо) и найденные поиском по теме. Если поиск
по теме попадал в соседнюю переписку — а у писем вида «Перемещение Королёв Стан
-Борисов» и «Перемещение Королёв Стан - Могилев» темы почти одинаковые, — метка
уходила **ещё и на неё**, а в таблицу ложился чужой id.

Дальше по этому id ломалось всё, что на него опирается: карточка показывала другое
письмо и другую дату, «Перейти к ветке» отвечало «Ветка не найдена», повторное
добавление правильного письма считалось дублем, а метка в почте стояла на чужом письме.

Теперь результат поиска принимается, **только если он про ту же переписку**: id из
поиска должны пересекаться с id перетащенного письма. Не пересекаются — метку получает
только перетащенное письмо, а в консоль печатается, что именно нашёл поиск и что было
на странице. То же правило применяется к колонке «ID письма»: id перетащенного письма
важнее результата текстового поиска.

Если id со страницы снять не удалось (письмо уже уехало из списка), поведение прежнее —
работаем по поиску.

## Сорока символов превью не хватало, чтобы различить письма

Начало текста письма («превью») — главный способ отличить две переписки с одинаковой
темой. Сравнивались первые **40** символов. Для писем по шаблону этого мало:

```
доброй ночи водитель прибыл на загрузку     ← первые 40 символов письма от 03:35
доброй ночи водитель прибыл на загрузку     ← первые 40 символов письма от 04:05
```

Ровно сорок символов, совпадающих дословно. Два разных письма одного дня выглядели
одинаковыми, и карточка показывала не то. Теперь сравнивается весь доступный общий
префикс (до 200 символов).

Там же добавился более точный якорь по времени: раньше для выбора ветки бралась дата
из таблицы, а она знает только **день**. Сохранённое время письма (`ts:` в колонке «ID
письма») знает минуты — по нему различаются два письма одного дня.

## Дата письма терялась из-за гонки двух запросов

Строка добавлялась двумя запросами к таблице, и они шли **параллельно** — с
комментарием «диапазоны не пересекаются». Они пересекались:

* первый пишет в `A<строка>` массив длиной во все используемые колонки, и в позиции
  даты там **пустая строка** (дату в него не кладут — её надо записать как дату, а не
  как текст);
* второй пишет дату в ту же ячейку с `USER_ENTERED`.

Кто ляжет последним, решал Google. Ложилась последней запись строки — дата затиралась
пустотой. Отсюда «иногда дата не проставляется, и от способа добавления это не
зависит»: дело было не в способе, а в гонке.

Теперь запросы идут строго по очереди: сначала строка, потом дата. Дата всегда
последняя и всегда доживает.

## Метка на экране убирается сама, а не ждёт синхронизации почты

Прошлая версия прятала плашку метки один раз. Этого мало: сразу после «Выполнено»
письмо закрывается, почта заново рисует список из своего кэша — и метка появляется
снова, уже на строке списка. Раньше её добивала кнопка «проверить новые письма», но
теперь письмо к этому моменту уже закрыто, и кнопка списка не перезагружает.

Поэтому плашка убирается не разово, а подметанием: несколько секунд подряд, пока почта
не синхронизируется сама. Плюс сравнение имени стало терпимее — внутри плашки есть
крестик «снять метку», он приклеивается к тексту («⁉️Уручье ✕»), и точное сравнение не
совпадало.

Уже спрятанная плашка второй раз в список не попадает: иначе запомнилось бы «было:
скрыта», и возврат при неудаче оставил бы её скрытой навсегда.

## «Выполнено»: метка исчезает сразу, письмо закрывается намеренно

Раньше после «Выполнено» письмо закрывалось, а метка пропадала мгновенно. Обоим этим
занималась кнопка почты «проверить новые письма», которую расширение жало после снятия
метки: она уводит во Входящие (отсюда и закрытие) и заодно перерисовывает список
(отсюда и мгновенно исчезающая метка).

Кнопку пришлось убрать при открытом письме — она закрывала письмо и посреди чтения,
когда никто не просил. Вместе с ней ушли обе полезные части. Возвращаем их по
отдельности и осознанно:

* **Метка убирается с экрана сразу**, ещё до того, как почта ответит: расширение прячет
  её плашку само — и в открытом письме, и в строке списка. Не удалось снять — плашка
  возвращается на место, чтобы экран не врал. Боковое меню при этом не трогается: там
  папка может называться так же, как метка.
* **Письмо закрывается намеренно** — кликом по текущей папке (а если её нет, возвратом
  по истории), и только по «Выполнено». Фоновым обновлениям уводить с письма
  по-прежнему запрещено.

Кнопка «Выполнено» в самой почте закрывает письмо всегда: она по смыслу действует на
открытое письмо. Галочка на карточке в панели — только если открыто **именно то** письмо,
которого она касается; чужое открытое письмо не трогается, его читают.

## Ярлычок не краснеет у того, кто сам добавил письмо

Плашка краснеет, когда состав её строк разошёлся с тем, что было при последней
синхронизации меток. Добавление письма состав меняет — но тому, кто добавил, краснеть
не из-за чего: расширение тут же поставило метку в его почте. Для этого есть
`noteSelfLabelChange`: она говорит «эту плашку меняли мы сами», и слепок перезаписывается
при следующей загрузке строк.

Вызывалась она только на пути «добавить письмо из панели». Добавление **из попапа**
(«Взять на контроль») её не вызывало: попап просит панель повесить метку сообщением
`pm-apply-label`, метка ложилась, а слепок не обновлялся — и у сотрудника ярлычок
загорался красным сразу после его же правильного действия, хотя в его почте всё стояло.

Теперь этот путь отмечает изменение своим и сразу просит перечитать строки. Отмечаются
**только реально поставленные** метки: `applyLabelForTopic` возвращает список тех, что
легли, и если метка не легла — красный сигнал остаётся, как и должен.

У всех остальных плашка по-прежнему краснеет: письмо коллеги в их почте метки не
получило, и это ровно тот случай, ради которого сигнал и сделан.

## Сторож стоит у самой кнопки, а не у одного из вызывающих

Журнал показал причину дословно:

```
⟐ открыто письмо (194217733931157435)                       адрес: #/message/194217733931157435
⟐ жму кнопку почты «проверить новые письма» (button… [Проверить, есть ли новые письма])
⟐ открытое письмо закрылось (было: 194217733931157435)      адрес: #/inbox
```

В этой сборке почты кнопка «проверить, есть ли новые письма» **уводит во Входящие**, а
`nudgeYandexRefresh()` звали из четырёх мест: `forceMailListRefresh`, `refreshEnvelope`,
простановка метки на письмо и добавление письма в таблицу. Сторож стоял только у
первого — остальные три жали кнопку при открытом письме.

Теперь проверка внутри самой `nudgeYandexRefresh`, то есть у опасной операции, а не у
одного из вызывающих. Пропущенное нажатие не теряется: оно откладывается и выполняется,
как только человек закроет письмо (за этим следит наблюдатель за открытым письмом).
Клик по папке не откладывается — он уводит с экрана, и делать это «когда-нибудь потом»
без просьбы нельзя.

## Кнопка «проверить новые письма» тоже уводит из письма

Сторож, поставленный в прошлой версии, стоял не в том месте: `forceMailListRefresh`
сначала вызывал `nudgeYandexRefresh()` и только потом смотрел, занят ли человек. А эта
«безобидная» функция жмёт кнопку почты «проверить новые письма», а если не находит её —
рассылает синтетические `focus` и `visibilitychange`. В этой сборке почты такой толчок
перезагружает страницу целиком: открытое письмо закрывается, консоль очищается — и
никаких следов, хотя сторож формально уже стоял.

Теперь проверка идёт ПЕРВОЙ: занят человек — не делаем вообще ничего, ни кнопки, ни
клика по папке.

## Переход к письму отменяется, если письмо открыли сами

Переход по клику на тему — это цепочка **отложенных** шагов: клик по папке → ждём
900 мс загрузки списка → до трёх секунд ищем строку в списке → и только потом, если не
нашли, уходим в поиск почты (`#/search?request=…`). Между первым и последним шагом
проходит несколько секунд, и за это время человек успевает открыть письмо сам. Тогда
последний шаг закрывал то, что он читает: «открыл письмо, а оно через несколько секунд
закрылось само».

Клик по папке тут ни при чём (его уже сторожит `mailBusyWithUser`) — уводил именно
переход к поиску, поэтому в консоли и не было ни строчки.

Теперь перед каждым отложенным шагом панель сверяет адрес с тем, что был на момент
клика. Адрес сменился на открытое письмо, и открыли его **не мы** — шаг отменяется, в
консоль пишется «переход отменён: вы открыли письмо сами, не мешаю».

Различать «мы открыли» и «человек открыл» нужно обязательно: панель и сама ходит по
`#/message/…`, а в раскладке «список слева, письмо справа» письмо открыто всегда. Поэтому
адрес, поставленный панелью, запоминается отдельно (`setMailHash`), и переход
отменяется, только если адрес изменился **и** новое письмо открыто не панелью.

## Поиск ждёт появления письма, а не судит с первой попытки

После отметки «Выполнено» почта перерисовывает список. Проверка «нашлось ли письмо»
делалась один раз через полторы секунды и попадала ровно в этот промежуток: выскакивало
«Ветка не найдена в списке», а мгновением позже письмо появлялось на экране. Теперь
письмо ждут до пяти секунд (проверка каждые 400 мс), и сообщение появляется, только
если его действительно нет.

## Красный крестик не остаётся от осечки запроса

Строка помечалась красным «письма в ящике нет», когда прогон меток не нашёл её письма.
Но не найти можно по двум разным причинам: письма правда нет — или запрос к почте не
прошёл (сеть, отказ авторизации). Второе метилось так же, крестик держался до
перезагрузки вкладки, и помогал только Ctrl+Shift+R.

Теперь красным метится только случай «почта ответила, письма нет»; осечка запроса
пишется в разбор прогона как «запрос к почте не прошёл». И наоборот: если строка
опозналась среди писем, на которых метка уже стоит, прежний крестик снимается сразу —
письмо явно на месте.

## Три разных «ноля» на плашках теперь различимы

Счётчик на плашке показывал «0» в трёх совершенно разных случаях, и отличить их было
нельзя:

| Что видно | Что на самом деле |
|---|---|
| `…` | ответа от таблицы ещё нет — читаем |
| `—` | прочитать не удалось; причина в подсказке при наведении |
| `0` | таблица ответила, строк для этой плашки действительно нет |

Плюс ответа могло не быть **вовсе**: служебный процесс расширения выгружается, порт
закрывается молча, и панель с попапом навсегда оставались в «загрузка…». Теперь оба
ждут с потолком в 20 секунд и показывают честную ошибку.

А если таблица ответила, но строк ноль, в консоль печатается разбор чтения: лист,
диапазон, сколько строк получено, сколько отброшено как выполненные и сколько — без
темы. Три причины «строк нет» больше не выглядят одинаково.

## Сорвавшееся чтение не обнуляет счётчики на плашках

Ошибку чтения панель показывала вызовом `render([], причина)`. А `render` присваивает
`latestRows` — то есть **один** неудачный ⟳ (или неудачная загрузка при старте) стирал
все строки из памяти панели, и счётчики на всех плашках становились нулями. Со стороны
это выглядело как «данные пропали», хотя таблица была на месте, а не прочитался один
запрос.

Теперь ошибка чтения показывается, **не трогая уже показанные строки**: список
остаётся прежним, а про сбой говорит тост «список показан из сохранённого». Если
показывать нечего (сбой на холодном старте), счётчики показывают «—», а не «0» — ноль
читается как «в таблице пусто», и это вводит в заблуждение; причина при этом лежит в
подсказке при наведении.

## Неудачное чтение таблицы не стирает уже прочитанное

Если чтение таблицы сорвалось (сеть, токен, доступ), расширение раньше клало в кэш
**пустой список** и обнуляло бейдж. Одна осечка — и панель показывала нули по всем
плашкам, а вернуться к нормальному виду могла только после следующего удачного чтения;
при постоянной ошибке — никогда. Выглядит это как «письма пропали», хотя в таблице всё
на месте и ничего не терялось.

Теперь при неудаче остаются последние успешно прочитанные строки, а причина
записывается рядом с ними. Бейдж продолжает показывать прежнее число. Время `updatedAt`
при этом не обновляется — оно остаётся временем последнего **успешного** чтения, поэтому
следующая попытка обновиться произойдёт как обычно.

Панель показывает такой список и отдельно говорит, что он **из сохранённого** и почему
не обновился, — вместо того чтобы молча стареть или молча обнуляться.

## Список писем показывается сразу, даже когда сеть молчит

`pm-get` (первый запрос панели и попапа) отвечает **из кэша немедленно**, если в нём
есть строки, а обновление уходит следом, не задерживая ответ.

Иначе панель зависит от сети и от молчаливого получения токена, а `chrome.identity`
умеет **не вызвать колбэк вообще**, когда для входа нужно окно. Тогда обещание не
разрешается никогда, ответа нет, и панель с попапом навсегда остаются в «загрузка…» —
при том, что в кэше лежат нормальные строки, а таблица подключена. Выглядит это как
«письма пропали».

Свежесть от этого не страдает: обновление придёт рассылкой, когда данные действительно
изменятся.

Когда показывать нечего (кэш пуст), обновления всё-таки ждём — но с потолком по времени
и с честной ошибкой. И **ошибку из кэша больше не прячем**: пустой список с ошибкой
внутри раньше отдавался как «ок, писем нет», хотя причина была в чтении таблицы.

## Отчёт всегда говорит, что стало с лишними метками

Письма с меткой, которых нет в таблице, раньше упоминались в отчёте, только когда они
находились. Если их не нашлось — про них не было ни слова, и после прогона оставалось
непонятно: их сняли или их просто не искали. Теперь отчёт заканчивается одним из двух:
«снимаю метку ещё с N писем вне таблицы» или «лишних меток нет».

## Консоль молчит, пока всё в порядке

Разбор прогона печатается коротко — одной строкой: сколько строк разбираем из скольких,
сколько пропущено, сколько писем с меткой вернула почта. По ней сразу видно, работает ли
экономия. Подробный разбор (два десятка полей) выводится, только когда есть на что
смотреть: выборка «кто носит метку» не удалась, либо не пропущено ни одной своей строки,
хотя выборка пришла. В обычном прогоне это был бы просто шум.

## «Хвосты» снимаются сами

Письма, на которых метка висит, а строки для них в таблице нет (метку повесили руками
в почте или строку удалили), больше не спрашивают разрешения. Раньше после каждого
прогона появлялся тост с кнопкой «Снять метки» — лишнее решение в конце работы. Теперь
метка снимается сама, фоном и в последнюю очередь, после отчёта. Сообщение появляется
только если снять не удалось.

## «Нет вообще меток на письмах» — два разных отверстия

Журнал сменщицы (панель 2.90.0) показал сразу оба.

### 1. Метки стояли — их просто не рисовали

Прогон `⁉️Заславль` отработал начисто: разобрано 15 строк, пропущено 7, ошибок нет,
ненайденных писем нет, «не применилось» нет. Метки не просто отправлены — прогон
**проверил их вторым запросом** к почте и получил подтверждение. А на экране их не
было.

Виноват сторож, стоявший с 2.53 у `nudgeYandexRefresh`: он откладывал нажатие кнопки
почты «Проверить новые письма» при **любой** занятости, в том числе когда показаны
результаты поиска. А человек в результатах поиска сидит почти всё время — панель сама
его туда и приводит. Отложенное нажатие ждало, пока он оттуда случайно выйдет: в
журнале это случилось **один раз за четверть часа**. Всё это время метки стояли в
почте, а список на экране был отрисован до их простановки.

Кнопку обвиняли зря. В том же журнале видно: нажатие из `#/search?request=«ООО Фидрик
и К»` оставило человека ровно там же — следующие строки идут с того же адреса. Письмо
закрывали не она, а запасной путь (синтетические `focus`/`visibilitychange`,
перезагружающие вкладку целиком) и `history.back()`.

Поэтому сторож сузился до того, что кнопка правда ломает:

* **открыто письмо** — не жмём, откладываем (читать никто не мешает);
* **результаты поиска, переход к письму** — жмём сразу;
* запасной путь без кнопки — сторож полный, как был;
* **клик по папке** (в `forceMailListRefresh`) — откладывается по-прежнему: он уводит
  с экрана, и делать это без просьбы человека нельзя.

### 2. Метку могли снять с живого письма — молча и навсегда

«Хвост» опознаётся от обратного: письмо с меткой, которое не заявила ни одна строка.
Это верно ровно настолько, насколько точно опознаны строки, — а у сменщицы в колонке
«ID письма» лежат id **чужого** ящика, и опознание идёт догадкой по теме, началу
текста и времени. Стоит догадке промахнуться на одну переписку из десятка с темой
«Перемещение Заславль - Таборы», и настоящее письмо строки оказывается «вне таблицы»:
метку с него снимают фоном, а ставят на соседнее. Именно так и выглядит «нет вообще
меток на письмах».

Теперь у снятия два предохранителя, и оба — от **живых невыполненных** строк плашки:

* **ветка (`tid`) уже заявлена своей строкой** — все её письма наши;
* **тема письма совпала с темой живой строки** — значит такая строка есть, и мы просто
  не смогли связать её с этим письмом.

Выполненные строки под предохранители не попадают: с их писем метку снимает обычный
путь («снять»), а он опирается на опознание, а не на догадку. О спасённых письмах
прогон говорит вслух — молчаливая защита так же непонятна, как молчаливое снятие:

```
«⁉️Заславль»: метку НЕ снимаю с 6 писем — они из веток живых строк плашки
(по ветке: 4, по теме: 2). Строку с ними связать не удалось: скорее всего,
id в таблице из чужого ящика.
```

Цена ошибки несимметрична и решает спор: лишняя метка никому не мешает и будет
предложена в следующий прогон, а снятая по ошибке теряется молча и навсегда.

### 3. «Плашку метки убрать не удалось» — чаще всего ложная тревога

Оба предупреждения в журнале сменщицы относились к письму «ООО "Фидрик и К"», которого
на экране уже не было: она к тому моменту ушла в другой поиск. Метка была снята через
API, прятать было нечего. Теперь, когда список на экране сменился, панель молчит (в
отладке остаётся строка «ушли с того списка, где было письмо»): ложная тревога потом
разбирается как настоящая поломка и уводит в сторону.

## Холостой ход: что панель перестала делать впустую

Раньше при открытой панели и **неизменной** таблице расширение раз в пять минут
переискивало в почте все строки. Теперь тик без изменений не стоит почти ничего.

| За час простоя (94 строки, 8 из них не найдены) | было | стало |
|---|---:|---:|
| Чтений таблицы | 12 | 12 |
| Запросов к почте | 2088 | **0** |
| Полных переотрисовок списка | 12 | **0** |
| Полных перезаписей кэша | 96 | **0** |

Что изменилось:

- **Отрицательный ответ теперь кэшируется.** Выход по свежему кэшу требовал наличия
  результата, а у строки «письма в этом ящике нет» результат как раз удаляется — то
  есть самый дорогой поиск (его не подтверждает ни глобальный, ни одна папка, поэтому
  обход идёт по всем папкам) повторялся каждый проход. Срок для «не найдено» — 30 минут,
  он длиннее обычного: письмо, которого в ящике нет, само там не появится.
- **Кэш поиска перестал протухать раньше времени.** `API_TTL` был 3 минуты при опросе
  таблицы раз в 5 минут — к каждому тику кэш каждой строки был уже просрочен. Стало
  10 минут, заведомо больше периода опроса.
- **Список не рассылается во вкладки, если не изменился.** `refresh()` слал `broadcast`
  безусловно, а каждая рассылка — это полная перерисовка списка в панели и перепоиск
  по всей таблице в почте.
- **`render()` не пересобирает список на тех же данных.** Заодно перестали слетать
  прокрутка и раскрытые карточки.
- **Вкладка в фоне ничего не переискивает.** Раньше смотрели только на «панель открыта».

## Мелочи того же прогона

- **Разметка почты разбирается один раз, а не на каждую строку.** Поиск письма по
  списку делал `querySelectorAll` объединением из шести селекторов и на каждой строке
  ещё цепочку из шести — и всё это по строке таблицы за раз (при 94 строках — 94
  одинаковых прохода в одном тике). Теперь список разбирается один раз и держится
  готовым индексом до ближайшего изменения разметки.
- **Кэш пишется одной записью на проход.** Сохранение кладёт кэш целиком, а звали его
  по строке за раз; теперь вызовы копятся секунду и сливаются в одну запись (перед
  закрытием вкладки дописывается принудительно).
- **Объём кэша в подвале считается не чаще раза в 15 секунд** и только при открытой
  панели: полная сериализация ради подписи шла из тех же горячих мест.
- **Отметка «Выполнено» не ждёт перечитывания таблицы.** Было три последовательных
  запроса на клик (сверка строки, запись, чтение всего листа); перечитывание теперь
  идёт вдогонку и склеивается — десять отметок подряд дают одно чтение вместо десяти.
- **«Обновить метки» читает лист один раз на весь прогон.** Каждая плашка запрашивала
  его сама, и на семи плашках лист читался семь раз подряд с одинаковым результатом.
- **Наблюдатель за списком писем работает только при открытой панели** и получил
  предельный срок ожидания: в виртуализированном списке прокрутка сбрасывала дебаунс
  снова и снова, и при долгой прокрутке он не срабатывал вообще.
- **Панель на старте больше не показывает старые данные.** Условие «пора обновить»
  смотрело на пустоту списка вместо его возраста: непустой кэш не обновлялся никогда,
  а честно пустой перечитывался при каждом открытии страницы.
- **Обновление, пришедшее во время написания комментария, не теряется** — раньше такая
  порция данных просто выбрасывалась; теперь она придерживается и применяется, как
  только поле отпустят.
- **Читается не всегда до колонки Z**, а до последней используемой; настройки таблицы
  не перечитываются из хранилища на каждое сообщение.

## Что и сколько хранится локально

В `chrome.storage.local` (это браузер конкретного сотрудника, не общая таблица) лежат:

| Что | Размер |
|-----|--------|
| Кэш найденных писем — по записи на строку таблицы | ≈ 0,7 КБ на строку |
| Слепки синхронизации меток | по строке чисел на метку |
| Место кнопки «Выполнено» | пара чисел |

Лимит `chrome.storage.local` — 10 МБ, то есть даже 10 000 записей (6,5 МБ) в него
влезли бы. Но раньше кэш рос **без чистки**: строку закрыла коллега или её удалили
из таблицы — запись оставалась навсегда. А сохраняется кэш целиком, одним куском на
каждое изменение, поэтому лишние тысячи записей просто замедляют запись.

Теперь после каждой загрузки строк выбрасывается всё, чему в таблице уже ничего не
соответствует, плюс страховка: записи старше 30 дней уходят в любом случае. Заодно
чистятся слепки меток, которых больше нет в настройках. Если кэш перевалит за 100 КБ,
его объём появится в подвале панели рядом со счётчиком записей.

## Письма с метками, под которые нет плашки

Строка «принадлежит» плашке по колонке «Метка». Строка **без** метки относится к
первой плашке. А если метка есть, но плашки с таким именем нет (список плашек
поменяли у себя или у сменщицы, а в таблице остались строки со старыми метками) —
раньше такая строка не попадала **никуда**: бейдж расширения её считал, а в панели
её не было ни в одной плашке. Выглядело это как «сверху 94, а в плашках 8, и
обновление будто не работает».

Теперь такие письма показываются в **первой** плашке и попадают в её счётчик, так что
сумма по плашкам сходится с бейджем. Сверху списка при этом висит предупреждение с
перечнем «чужих» меток и кнопкой **«Завести плашки для этих меток»**. Кнопка работает,
даже если когда-то нажали «Не сейчас» в окне про новые метки коллег.

Важно: кнопка 🏷️ первой плашки такие письма **не трогает** — у них своя метка, и
ставить на них метку первой плашки было бы неверно. Чтобы их метки синхронизировались,
нужно завести под них плашки.

## Счётчики на плашках

Счётчик обновляется не только при открытии панели, но и при возврате к почте:
переключении вкладок/окон и переходе между папками внутри почты (с тротлингом — не
чаще раза в 45 секунд). Панель при этом открывать не нужно: когда в один день
работают вдвоём, письма коллеги появляются в счётчике сами. Перепоиск писем в самой
почте по-прежнему идёт только при открытой панели — при закрытой эти данные не видны.

## Оформление плашек

Для каждой метки в Настройках задаются:

| Настройка | Что делает |
|-----------|-----------|
| Цвет | Фон плашки и чипа метки в карточке. |
| Цвет текста | Любой — не только белый или чёрный: у пастельных плашек чёрные буквы выглядят тяжело, а текст в тон фону читается мягче. Подложка счётчика подбирается по яркости выбранного цвета. |
| Непрозрачность, % | 100 — сплошной цвет, меньше — плашка просвечивает. Ниже 10 % не опускается, иначе её не найти. |

## Имена меток: эмодзи значимо, невидимое — нет

Эмодзи в имени метки — **значащая часть названия**. «⁉️Барановичи» (ставится вручную,
«на контроле») и «Барановичи» (её вешает правило обработки почты) — разные метки, и
путать их нельзя: иначе расширение сняло бы автоматическую метку почты как «хвост».

А вот **невидимые** различия при сравнении убираются:

- селектор начертания `U+FE0E`/`U+FE0F` — «⁉» и «⁉️» это один и тот же символ с
  необязательным «показать как эмодзи», и почта отдаёт его то так, то так;
- символы нулевой ширины (`U+200B`–`U+200D`, `U+FEFF`);
- разные формы записи одного символа — приводятся через `NFC`.

Из-за такого невидимого различия метка «⁉️Архив» из настроек не совпадала с «⁉Архив»
в почте: расширение считало её отсутствующей и **создавало заново**.

## Если метки «не находятся в почте»

Список меток берётся из модели `labels` web-api. Формат ответа у разных сборок почты
разный, поэтому разбор идёт в три захода: известные поля → поиск по структуре во всём
ответе → **ссылки бокового меню почты** (`#/label/<lid>`). Последний источник
выручает, когда модель ответила в незнакомом виде: без `lid` не работает ни
простановка метки, ни снятие.

## Поиск не остаётся внутри прежней папки

Когда ветку показывают поиском почты, расширение вписывает запрос в поисковую строку.
Но почта помнит выбранную ранее папку или метку — она висит чипом рядом с полем
(«Королёв Стан ✕»), — и новый запрос уходит **внутрь неё**. Ищешь письмо из плашки
«Архив», а почта отвечает «в папке Королёв Стан ничего не нашлось». Поле при этом
очищается, поэтому со стороны выглядит так, будто расширение ищет не там.

Оказалось, что область поиска почта держит **в самом адресе**:

```
#/search?request=<запрос>            — по всему ящику
#/search?request=<запрос>&fid=<id>   — внутри папки
```

Поэтому расширение больше не печатает запрос в поле, а **переходит по адресу без
`fid`** — это гарантированно поиск по всей почте. Печать в поле осталась запасным
путём: если сборка адрес не поняла (после перехода в адресе нет `search`), работает
прежний способ.

Клик по папке в боковом меню для «жёсткого сброса» пробовался и оказался вредным:
он переводит почту В эту папку, и следующий запрос уходит внутрь неё — ровно та беда,
от которой лечились.

Чип рядом с полем («Королёв Стан ✕») может остаться висеть от прошлого поиска — на
область поиска это уже не влияет, её задаёт адрес. Крестик всё равно нажимается (есть
несколько написаний селектора), а если не нашёлся — разметка чипа один раз печатается
в консоль, чтобы селектор можно было добавить, не разыскивая элемент вручную.

Если почта сама дописала папку в адрес поиска, это тоже видно в консоли — вместо
молчаливого «ничего не нашлось».

## Поиск по папке: имя поля берём у почты и проверяем по ответу

Приоритет папок («Отправленные» проверяем последними, чтобы метка не ушла на свою же
копию письма) держится на поиске, ограниченном одной папкой. Раньше идентификатор папки
уходил в запрос под жёстко зашитым именем `fid`. В сборке, где поле называется иначе,
почта **молча игнорировала** его и отвечала письмами со всего ящика: «поиск по папке»
был обычным поиском, приоритет не действовал, а понять это можно было только косвенно —
по тому, что обход папок ничего не находит.

Теперь:

* имя поля берётся у самой почты — из её собственного запроса поиска или открытия папки
  (`inject.js` запоминает их наравне с «конвертом»);
* результат **проверяется по ответу**: все ли письма действительно из запрошенной папки.
  Пришли письма из других — поле проигнорировано, пробуется следующее написание
  (`fid` → `folder_id` → `folderId`);
* подтверждённое имя сохраняется в `chrome.storage.local` (`pm_folder_key`) — перебор
  не повторяется при каждой перезагрузке;
* пустой ответ уликой не считается: письма в этой папке может просто не быть, и гонять
  из-за этого лишние запросы незачем;
* если ни одно написание не сработало, поиск по папкам отключается (как и раньше,
  чтобы не бить по API зря), но в консоли теперь написано, что делать: один раз найти
  что-нибудь через поиск почты, **находясь в папке**, — расширение подсмотрит поле.

Косвенная улика «по папкам не нашли, а глобально нашли» осталась, но больше не
отменяет **подтверждённое** поле: письмо могло лежать в папке, которой нет в боковом
меню.

## Голого совпадения времени мало, чтобы разбирать чужую строку

Строки соседних плашек нужны прогону только чтобы **снять** метку — а снимать нечего,
если её там нет. Отбирались такие строки по «слабому» совпадению с письмами, на
которых метка стоит: по теме **или** по времени (±12 часов).

Совпадение одного только времени опознанием не является: за полсуток в ящик приходят
десятки писем, и почти у каждой строки таблицы найдётся помеченное письмо в этом окне.
На плашке с **одной** своей строкой в разбор уходило **74** — почти вся таблица, каждый
прогон, впустую. Со стороны это выглядело так: открываешь плашку, письма в ней давно без
часиков, а часики на самой плашке крутятся ещё полминуты — расширение в это время
разбирало чужие строки.

Теперь чужая строка идёт в разбор только при совпадении по **id или теме**. Метка при
этом нигде не остаётся висеть: письмо, которое не заявила ни одна строка, снимается в
конце прогона как «хвост» — одним запросом на всех, без поиска по каждой строке.

В консоли после каждой плашки печатается, сколько она работала и сколько строк разобрала.

## Почему плашка иногда «пропущено 0»

Пропуск «метка уже стоит» держится на времени письма: id у каждого ящика свои, а время
одинаково у всех, и именно по нему строка опознаётся среди писем с меткой. У строк,
заведённых до появления этой колонки (или в чужом ящике), времени нет — и такая строка
каждый раз идёт в полный разбор, сколько бы раз метка уже ни стояла.

Прогон дописывает время таким строкам сам. Теперь он ещё и говорит об этом в консоли:
«дописано время письма в N строк — в следующий прогон они пропустятся без запросов к
почте». То есть «пропущено 0» на плашке — не поломка, а разовая цена: со следующего
прогона эти строки становятся быстрыми.

## Ветки с неполной выборкой отчёт называет поимённо

Если поиск вернул письмо без id переписки, спросить у почты «покажи всю ветку» не у
чего, и метку получают только найденные письма. Раньше отчёт сообщал лишь количество
таких веток — искать их приходилось вручную по всему списку. Теперь после прогона в
консоль печатается таблица: тема, строка таблицы, сколько писем попало в выборку и
почему она неполная.

## Переход к письму из панели

Строка письма в списке ищется **от точного к грубому**, тремя проходами:

1. **id письма ЭТОЙ строки** (`shownMid`) — точным совпадением, а не «содержит».
2. **Остальные id ветки.** Свёрнутая ветка рисует в списке ОДНО представительское
   письмо, и его id обычно не тот, что у нашего, — но переписка та же, и разворачивать
   надо именно эту строку. Раньше второго прохода не было: искали строго по id письма
   строки, и на свёрнутой ветке поиск давал пусто.
3. **Тема строки** — а не весь её текст (иначе достаточно было совпадения по названию
   поставщика в цитате). Но только **с подтверждением** — см. ниже.

### Одинаковая тема — разные письма: строка выбирается по дате и по началу текста

Совпадения по теме мало: «Энергия ООО» в понедельник и в четверг — **разные**
переписки. Раньше из подошедших по теме строк бралась просто **первая**, а список
отсортирован свежими вверх — поэтому в своей папке «показать ветку» открывало самое
новое однотемное письмо вместо нужного.

Теперь собираются **все** подошедшие по теме строки, и нужная выбирается по приметам:

1. **Начало текста письма** (колонка «Текст письма») — самая надёжная примета среди
   писем одного дня. Сравнивается весь общий префикс, а не первые 40 символов: письма
   по шаблону («Доброй ночи. Водитель прибыл на загрузку …») совпадают первыми сорока
   символами дословно.

   **Непопадание здесь — это улика, а не «нет данных».** Если начало текста нужного
   письма известно, у строк списка оно читается, и не совпало ни с одной — значит
   перед нами другие письма, и дальше по дате решать нельзя. Раньше пустой результат
   просто игнорировался, и решала дата — а когда у обеих веток последнее письмо
   пришло в один день, дата их не различает вовсе. Отсюда и было: щёлкаешь одну
   строку, а подсвечивается ветка соседней, с той же темой.

   Отказ действует только там, где за шагом есть следующий (папка, прокрутка, поиск).
   На последнем шаге ближайшее однотемное письмо всё равно показывается.
2. **Дата письма.** В списке почта показывает дату **последнего** письма ветки, и
   откуда взято время — важно:
   - время последнего письма из ответа почты — сверяем **день в день** (допуск сутки:
     часовые пояса и письма около полуночи);
   - **дата письма из таблицы** — это начало переписки: нужная строка не может быть
     старше неё, но запросто свежее — на все ответы, пришедшие с тех пор. Поэтому
     среди строк не старше этой даты берётся **самая ранняя**: те, что свежее, — уже
     другие письма.
3. Дата известна, но ни одна однотемная строка к ней не подходит → **ничего не
   возвращаем**. Открыть письмо другого дня хуже, чем не открыть ничего.

### Что именно сломалось между 2.49 и 2.71

`findMessageInList` — сам разбор списка — **не менялся вообще**. Сломала одна строка
в `openThread` (2.68, `255c61f`):

```js
// было (2.49):
findMessageInList(topic, info.tid || info.mid, info.mids)
// стало (2.68):
findMessageInList(topic, rowMid || (info.tid || info.mid), rowMid ? [rowMid] : info.mids)
```

`rowMid` — id **письма**. А строка списка у свёрнутой ветки отдаёт id **ветки**
(`data-react-focusable-id="t193…"`), и раньше он попадал в набор первым (`info.tid`).
С 2.68 при известном `rowMid` из набора выпали и `tid`, и все `mids` — id ветки
сверять стало не с чем, строка не находилась НИКОГДА, и переход каждый раз уходил по
всей цепочке: папка → прокрутка → поиск → «ветка не найдена».

В 2.67–2.68 это прикрывал фолбэк «не нашли — открываю письмо по id»; в 2.71
(`413a173`) фолбэк убрали, а сужение оставили — и симптом вылез наружу.

Сейчас проходов три, и `tid` с `mids` вернулись во второй.

### Отказ — только там, где за шагом есть следующий шаг

Если по теме что-то подошло, разбор **всегда** что-то возвращает. Единственное
исключение — `strictDay`: за шагом есть ещё шаги (папка, прокрутка, поиск), и строку
заведомо другого дня лучше пропустить, её найдёт следующий шаг. На последнем шаге —
в результатах поиска — строгость снимается: лучшая догадка на экране полезнее пустого
отказа, до 2.68 так и было.

Наглухо отказывать нельзя: получается «показала результаты поиска, выделить не
удалось» вместо переписки, которая тут же, на экране.

### Тема без номера уходит в поиск В КАВЫЧКАХ

Без кавычек почта разбирает тему на слова, и выходит совсем не то:

```
Перемещение Королёв Стан -Борисов   →   3339 писем
```

Две причины, и вторая хуже первой:

1. Ищется **любое** из слов — в выдаче «Перемещение Королев Стан — Таборы»,
   «Перемещение Заславль ДХ — Королёв Стан» и десятки других чужих переписок.
2. `-Борисов` почта читает как **оператор исключения**: минус перед словом означает
   «без этого слова». То есть нужное письмо выбрасывалось из выдачи ровно тем куском
   темы, который его и опознаёт.

В кавычках «-» — обычный символ фразы, а не оператор, и ищется вся тема целиком.

Порядок при этом не меняется: **есть номер — ищем по номеру, как раньше**; кавычки
включаются только там, где номера нет. И только на последнем шаге — папка, дата, тело
и время по-прежнему отрабатывают до него.

Повторный запуск того же поиска в первые секунды гасится — это защита от двойного
клика и наложения отложенных шагов. Ключ у неё — **тема плюс номер**, а не одна тема:
у складских строк темы совпадают буквально («Перемещение Партизанский - Таборы» и
«Перемещение партизанский - таборы» после нормализации одинаковы), а номера разные.
По одной теме клик по соседней строке в первые секунды просто проглатывался —
«щёлкаю, и ничего не происходит».

Запросы идут очередью, каждый следующий шире предыдущего, и следующий берётся, только
если почта не нашла **ни одного** письма — то есть текущий уже провалился:

```
номер  →  тема в кавычках  →  тема без кавычек
```

Номер остаётся самым точным путём, и на нём всё и остаётся. Тема вида

```
TIANJIN TEXTILE GROUP IMPORT AND EXPORT INC. Перемещение товаров СВХ (Колядичи)-0000-0342359
```

содержит номер `0000-0342359` — по нему и ищется. Ни скобки, ни точки, ни тире в запрос
не попадают и операторами стать не могут. Но если номер в почте не найдётся (его
переписали, письмо переслали без него), раньше на этом всё и кончалось — теперь
пробуется тема. Последний запрос очереди — тема без кавычек, ровно прежнее поведение.

### Метка, снятая при работе по списку, больше не «возвращается»

Плашку снятой метки панель убирает с экрана сама: Яндекс метки, поставленные через
API, в уже отрисованном списке не показывает, а кнопку «проверить новые письма» жать
нельзя — она закрывает открытое письмо и выбрасывает из результатов поиска.

Подметание длилось шесть секунд, и этого хватало ровно в одном случае: человек читал
письмо в папке, оно закрывалось, адрес становился `#/inbox` — почту сразу тормошили, и
метка уходила по-настоящему.

**При работе по списку так не выходит.** Открыли письмо из результатов поиска, нажали
«Выполнено», письмо закрылось — и адрес снова `#/search`. Для сторожа это «человек
занят», обновление откладывается и ждёт, пока человек уйдёт из поиска. Через шесть
секунд подметание кончалось, почта дорисовывала плашку из своего кэша — и метка «не
снималась до обновления страницы», хотя в почте её уже не было.

Теперь пока обновление отложено — подметание продолжается; когда оно наконец
случится, домётываются обычные несколько секунд.

### Метка ПОЯВЛЯЕТСЯ так же молча — та же дыра, с другой стороны

Сторож, из-за которого не исчезала снятая метка, ровно так же мешал и поставленной.
После перетаскивания письма панель звала `nudgeYandexRefresh()`, а он в результатах
поиска откладывал нажатие «на потом» — и плашка на строке не появлялась. Выглядело
как «метка не проставилась», хотя в почте она уже стояла.

Теперь после простановки идёт та же тихая синхронизация, мимо сторожа. И на успехе
панель больше не молчит: «Метка «⁉️Королёв стан» поставлена» — иначе «не появилась»
выглядит одинаково и когда метки правда нет, и когда список ещё старый.

Проверка «метка видна на строке» (`ensureLabelVisible`) тоже перестала выбрасывать
человека из поиска: полная перерисовка списка (клик по папке) осталась только там,
где человек ничем не занят, а в поиске — тихая синхронизация.

### Дубль при добавлении: одна тема — ещё не одно письмо

Проверка дублей с самой первой версии искала так: **совпал номер ИЛИ совпала тема**.
Ничего другого она не смотрела. Для складских тем это слишком грубо: «Перемещение
Королёв Стан — Могилев» носят десятки **разных веток**, и вторую в таблицу было не
добавить — расширение считало её дублем первой.

Теперь слабое совпадение «та же тема» отсеивается, как только видно, что письма
разные. Смотрим то, что письмо отличает, — ровно то, что уже лежит в таблице:

1. **id письма** (колонка «ID письма»). Сверяем, только если обе стороны из **одного
   ящика**: пометка `u:<uid>` говорит, чей ящик выдал эти id, а у сменщицы они свои —
   их непересечение ничего не доказывало бы.
2. **время письма** (`ts:`). Оно одинаково во всех ящиках — самая надёжная примета,
   когда id сравнить нельзя. Допуск две минуты.
3. **начало текста** (колонка «Текст письма»). Последняя примета: у разных писем одной
   темы тела разные.

Отсеиваем **только при доказательстве различия**. Сравнить нечем — считаем дублем, как
и раньше: одно и то же письмо не должно лечь в таблицу дважды.

Совпадение по **номеру** остаётся сильным и не отсеивается ничем.

### Дубль при добавлении: сообщение говорит, ЧТО совпало

Проверка ищет дубль и по номеру, и по теме — достаточно любого. А сообщение всегда
писало про номер:

```
⚠️ Номер «» уже есть в таблице (строка 247) и не выполнен. Всё равно добавить?
```

У письма без номера получалось «Номер «»» — сообщение ни о чём, притом что на деле
совпала **тема**, а письмо другое: та же переписка, но новое письмо в ней.

Теперь проверка сообщает, что именно совпало, и текст говорит правду:

```
⚠️ Письмо с такой же темой уже есть в таблице (строка 247) и не выполнено.
Тема: «ООО "ЛПР-Инвест"»
Если это другое письмо той же переписки — добавляйте.
```

Совпал номер — так и написано, с номером. Пустой номер, как и раньше, не совпадает
ни с чем: строки без номера дублями друг другу не становятся.

### Метка исчезает молча — без обновления страницы

После «Выполнено» метку снимаем через API: **в почте её больше нет**. Но Яндекс
свой уже отрисованный список не пересобирает и продолжает показывать плашку.

Заставить его пересобрать список можно только сменой адреса — уйти и вернуться. Это
работало, но выглядело как самостоятельное обновление страницы: список мигал.
А нужно оно было **не для самой метки** (её уже нет), а только чтобы перерисовать
кэш почты.

Поэтому адресом больше не двигаем. Остаётся:

1. **тихая синхронизация** — кнопка «проверить новые письма» отрабатывает молча,
   никуда не уводя (сторож её здесь не держит: «Выполнено» — не фон, человек сам
   нажал, и письмо мы всё равно закрываем);
2. **подметание** — плашка прячется у себя на экране, пока человек стоит на том же
   списке. Стоит ему перейти куда угодно — почта запрашивает список заново, и метки
   там уже нет.

До версии 2.53 кнопку жали без разбора, и метка так же исчезала. В 2.53 внутрь
`nudgeYandexRefresh` поставили сторож (кнопка закрывала письмо посреди чтения), и
заодно закрыли этот путь: в `#/search` она больше не жалась. Обновлять стало некому —
отсюда и было «метка не снимается, пока не обновишь страницу».

### Подметание начинается на ОТКРЫТОМ письме — и не должно умирать при его закрытии

Это оказалось причиной «один раз снялась с запозданием, второй раз не снялась».

Подметание запускается в момент нажатия «Выполнено», когда письмо ещё **открыто**, и
адрес тогда `#/message/…`. Через секунду письмо закрывается, адрес становится адресом
списка — и проверка «адрес тот же» решала, что человек ушёл, и сворачивала подметание
через несколько секунд. То есть оно успевало посмотреть только на разметку **открытого
письма** и заканчивалось до того, как отрисуется список.

Видно это было прямо в разборе:

```
    плашек на экране видели: 1 («Метка»)
```

«Метка» — это **кнопка на панели инструментов почты**, единственное, что похоже на
плашку в окне открытого письма. Строк списка подметание не видело ни одной.

Теперь открытое письмо адресом списка не считается: пока оно открыто, подметание ждёт.
Заодно адрес приводится к общему виду — почта переписывает `%20` в `+`, и сравнение
«та же строка» ломалось на ровном месте.

В разбор добавлена строка «строк письма на экране видели» — по ней сразу видно, дожило
ли подметание до списка вообще.

### Подметание живёт, пока человек не ушёл со списка

Шести секунд не хватало: почта перерисовывает список из своего кэша позже — и плашка
возвращалась. Теперь подметание держится, **пока адрес не сменился**: тот же список
— значит почта его не перезапрашивала, и плашку надо держать спрятанной. Ушёл —
домётываем несколько секунд и заканчиваем. Предел на всякий случай четверть часа,
чтобы ничего не мело вечно.

### «Иногда снимается, иногда нет» — это гонка со временем

Порядок событий после «Выполнено» такой:

1. метку снимаем через API — в почте её больше нет;
2. плашку прячем сами: Яндекс метки из API в уже отрисованном списке не показывает;
3. попросить почту перерисоваться **нельзя** — кнопка «проверить новые письма»
   закрывает открытое письмо и выбрасывает из результатов поиска. Нажатие
   откладывается до момента, когда человек уйдёт из поиска;
4. когда оно наконец случается, почта рисует список **заново** — свежими узлами, на
   которых нашего `display:none` нет.

Если к этой секунде подметание уже кончилось — плашка возвращается и живёт до F5.
Успело — «снялась». Не успело — «не снялась». Разница только во времени, поэтому и
«через раз»: сколько секунд человек пробыл в результатах поиска, столько и решало.

Значит мести надо не шесть секунд, а пока почта не догонит: теперь **три минуты**,
часто первые десять секунд и реже дальше.

### Ветка из нескольких писем — это несколько строк, и метка на всех

В результатах поиска почта показывает **каждое письмо отдельной строкой**. У переписки
из двух писем это две строки, и метка стоит на обеих. Подметание же искало **одну**
строку — значит вторая оставалась с плашкой, и человек видел «метка не снялась».

Поэтому разбор идёт теперь **от плашки к строке**, а не наоборот: берём все плашки
с нужным именем и у каждой проверяем, на нашем ли она письме. Так убираются сразу все,
сколько бы писем в ветке ни было.

Заодно это **дешевле**: разбор id строки стоит обхода всех её узлов, а плашек с нужным
именем на экране единицы — тогда как строк в списке бывает под тысячу.

### Почему нельзя было просто мести дольше — и при чём тут id

Подметание било по **всему экрану** по имени метки, а у соседних строк та же метка
стоит по делу. Три минуты такого — и человек решит, что метки слетели у половины писем.

Значит надо знать, где на экране **наше** письмо. Привязаться к одним лишь id из
колонки «ID письма» нельзя: у каждого ящика id **свои**, и у строки, заведённой
сменщицей, они чужие — не найдутся никогда, и подметание не сделало бы ничего.

Поэтому строку подметание опознаёт ровно так же, как её опознаёт переход к ветке:
**id → тема → дата письма и начало текста**. Свои id срабатывают сразу; чужие просто
не совпадут, и дело сделают тема с датой. Ищем каждый раз заново — почта перерисовывает
список, и прежний элемент становится чужим.

Если примет строки нет вовсе, остаётся прежний короткий проход по всему экрану.

Если убрать не удалось **ни одной** плашки, в консоль печатается разбор — молчать
здесь нельзя, именно этот случай человек и видит как «метка не снялась»:

```
Плашку метки убрать не удалось.
    снимали: «⁉️Королёв стан»
    плашек на экране видели: 4 («⁉️Королёв стан», «Королёв Стан», «Архив»)
    из них совпало имя: 2
    из них на нужном письме: 0
    приметы письма: тема «0000-0751081 ZHONGSHAN LINKTEX…», id 2 шт., дата 27.08.2026, 09:24
```

Три числа сразу называют причину: плашек не видели вовсе (список не отрисован), не
совпало имя (в почте метка называется иначе, чем в настройках) или не опознали строку
(приметы не сошлись).

### Когда переход не удался, панель говорит почему

Само «выделить не удалось» не объясняет ничего. Поэтому при срыве в консоль печатается
разбор: сколько строк в списке, сколько id искали, у скольких строк id вообще есть в
разметке, сколько строк подошло по теме, у скольких удалось прочитать дату, какой был
якорь времени и точный ли он, и на чём разбор остановился. Рядом — запрос, который ушёл
в поиск. Одного клика достаточно, чтобы назвать причину, без включения отладки.

Печатается **текстом**, а не объектом: консоль сворачивает объект в «Object», и
диагностика, ради которой всё затевалось, остаётся нераскрытой.

### Нет id в разметке — ещё не «ветки нет»

Идентификатор письма расширение снимает из ответа почты, а строка списка отдаёт его
в `data`-атрибутах — и в части вёрсток (в том числе в выдаче поиска) их там просто
нет. Раньше на этом месте был безусловный выход, и «показать ветку» отвечало
**«Ветка не найдена в списке»** при живой переписке прямо на экране.

Теперь при промахе по id разбор идёт дальше по теме — но **только когда есть чем
подтвердить** строку: время письма или начало текста. Без подтверждения выход
прежний: лучше честно не найти, чем открыть чужое письмо с такой же темой.


- **Клик по теме карточки** — «показать ветку»: расширение находит письмо по его id,
  при необходимости переключает папку, докручивает виртуализированный список почты
  до нужной ветки, подсвечивает её и разворачивает inline. Список писем при этом не
  пропадает с экрана. Если ветку найти не удалось — фолбэк на поиск почты.

### Что уходит в поисковую строку почты

Запрос строится **так же, как его строит собственный поиск расширения** (`apiGetInfo`):
есть номер ЗП/Перемещения — ищем **по номеру** (он находит письмо, даже когда в теме
его нет); номера нет — по **очищенной теме** (без хвоста вида `, 10:41`: по теме со
временем поиск не находит ничего).

Раньше в запрос уходили тема **и** номер сразу:

```
0000-0728699, ООО ТК Зелёная Русь-исправить ЗП "0000-0728699"
```

Такой длинный запрос с запятыми, тире и кавычками почта нередко не находит вовсе — и
это было прямой причиной «ветка не найдена» при живой переписке в ящике. С переходом
поиска на адрес (`#/search?request=…`) запрос стал значить ещё больше: что написано,
то и ищется.

Если после ожидания результатов строку выделить так и не удалось, сообщение это и
говорит — «показала результаты поиска, саму ветку выделить не удалось»: результаты
при этом **на экране**, искать глазами есть где. Прежнее «Ветка не найдена в списке»
звучало как «письма нет в ящике», хотя оно тут же, в списке результатов.

### Сколько запросов уходит в почту

Раньше поиск ветки шёл **постадийно по папкам**: по запросу на каждую папку, пока
ветка не найдётся, — и так для КАЖДОЙ строки таблицы. При десятке папок и трёх
десятках строк это сотни последовательных запросов: почта заметно тормозила, а часть
запросов упиралась в таймаут — отсюда «поиск срабатывает с четвёртого раза».

Теперь сначала делается **один обычный поиск по всему ящику**, и обход папок
включается, только если он ничего не подтвердил. Точность не страдает: результат
проверяется тем же строгим отбором (id → тема → тело), что и раньше. На замере
(3 строки, 10 папок, ветка в неучтённой папке) — 33 запроса против 3.

Опрос кнопки «Выполнено» тоже стал дешевле: он шарит по разметке открытого письма
селекторами вида `[class*="Label" i]`, которые браузер не умеет ускорять. Пока адрес
письма не менялся, разметка опрашивается раз в 3 секунды вместо 700 мс, а области
поиска отсортированы от узкой к широкой (раньше первой шла вся переписка целиком).

### Порядок перехода: папка → id → поиск

Шаги идут от точного к грубому, поиск по тексту темы — всегда последний:

1. Ветка видна в текущем списке → просто разворачиваем её на месте.
2. Ветка **старая** (последнему письму больше 6 дней) → показываем её **поиском
   почты**: тема уходит в поисковую строку, а нужная строка результата
   подсвечивается и разворачивается по счётчику писем (по самой строке не кликаем —
   это открыло бы письмо).
3. Иначе знаем папку ветки (`fid`) и нашли её в боковом меню → **переключаемся на
   папку** и докручиваем список до ветки, но не больше **шести экранов**. Раньше
   предел был 6000 шагов — четверть часа прокрутки, после которой всё равно
   включался поиск; в большой папке казалось, что расширение зависло.
4. Ветку так и не нашли (или папка неизвестна) → снова поиск почты. Прокручивать
   текущую папку в этом случае бессмысленно: ветка может лежать совсем в другой.

**Хеш-перехода (`#/message/<id>`) в переходе к ветке нет вообще.** В этой сборке
почты он открывает не переписку, а одно сохранённое письмо из её середины: сверху
вместо темы «(Без темы)» (у ответа своей темы нет), остальные письма под «Ещё N
писем». Так ведёт себя и переход по id письма, и переход по id ветки — поэтому
переход убран целиком, а не «поправлен». Ветка показывается только тем, что
заведомо показывает список: строкой в списке, папкой или поиском почты.

**Возраст ветки** ищется в трёх местах по очереди: время писем из ответа поиска →
метка `ts:` в колонке «ID письма» → **дата письма из таблицы**. Последний якорь есть
всегда (колонка обязательная), и именно его не хватало: когда панель ещё не успела
обновить строку, а колонка «ID письма» у сотрудника выключена, возраст считался
неизвестным, ветка проходила как свежая и открывалась переходом по id. Отсюда и было
«у меня работает, а у коллеги через раз».

Возраст ветки считается по **последнему** письму, а не по первому. Раньше брали
первое: переписка, начатая полгода назад, но с ответом сегодня, считалась «старой»,
хотя лежит в самом верху «Входящих» — и клик по карточке сразу вбивал тему в
поисковую строку почты, где первым выпадал чужой похожий разговор.

Идентификаторы из колонки «ID письма» для перехода **не** используются: они сняты из
ящика того, кто добавлял письмо, а у каждого сотрудника свои id. Для перехода годятся
только id, найденные поиском в текущем ящике; из таблицы берётся лишь временная
метка `ts:` — по ней и определяется возраст ветки, пока поиск ещё не отработал.

### Какая сборка сейчас загружена

После замены файлов расширение нужно **перезагрузить** на `chrome://extensions`
(кнопка ⟳ на карточке) — иначе браузер продолжает крутить старую сборку. Проверить
версию можно двумя способами: в консоли почты при загрузке печатается строка
`[Проблемные письма] панель версии 2.27.3`, и та же версия видна в подвале панели
рядом со счётчиком сохранённых записей.
- **«📩 Перейти к последнему письму»** — открывает конкретное письмо по `#/message/<mid>`.

## Пустой текст письма в карточке

Почта в ответе отдаёт начало текста (`firstline`) не всегда: у части писем оно
приходит пустым — это видно и в журнале панели, где такие письма печатаются с
`"начало": ""`. Раньше на это место подставлялось «письмо найдено», и стояло оно ровно
там, где идёт текст письма, — поэтому и читалось как его содержимое. Сообщать «письмо
найдено» в слоте текста и незачем: раз карточка показывает дату, автора и число писем,
письмо очевидно найдено.

Теперь там «(без текста)», курсивом и приглушённым цветом. Текст из колонки «Текст
письма» на это место не подставляется нарочно: он снят в момент перетаскивания, то
есть относится к первому письму ветки, а карточка показывает опознанное письмо
строки — обычно другое.

Заодно исправлена ошибка, которая из-за этой подписи и жила. Заглушка попадала не
только на экран, но и **в данные** (`info.lastPreview`), а там начало текста — третья
примета строки после темы и даты, единственная, что различает однотемные письма одного
дня. Проверка на заглушку стояла ПОСЛЕ выбора источника:

```js
let preview = (info.lastPreview || info.preview) || '';
if (preview === 'письмо найдено') preview = '';   // ← обнуляло совсем
```

То есть если почта не вернула текст, строка теряла эту примету **полностью** — хотя в
колонке «Текст письма» она лежала и была готова к употреблению. Теперь заглушка
отсеивается до выбора источника, и текст из таблицы доходит:

| `lastPreview` (от почты) | `preview` (из таблицы) | было | стало |
|---|---|---|---|
| заглушка | «недовоз принят…» | `""` | «недовоз принят…» |
| пусто | «недовоз принят…» | «недовоз принят…» | «недовоз принят…» |
| «скан запросила» | «недовоз принят…» | «скан запросила» | «скан запросила» |

## «Это письмо не найдено среди невыполненных строк таблицы»

Кнопка «Выполнено» у открытого письма ищет его строку в таблице. Проб было три:
сохранённый id письма, id всей его переписки, точное совпадение темы. Все три мимо —
и кнопка честно отвечала «не найдено», хотя строка есть и видна в самой панели.

Как это выходит на живом примере:

| | значение |
|---|---|
| тема письма | `СМАРТЛИНК ООО, 0000-0804943 `**`0000-0804939`**` запрос УПД без НДС` |
| тема строки | `СМАРТЛИНК ООО, 0000-0804943 запрос УПД без НДС` |
| «ID письма» строки | `t194217733931038109,…,u:`**`1130000025509844`** |
| наш ящик | `1130000018626852` |

* **По id не сходится**: строку завела сменщица, в колонке id ЕЁ ящика (пометка `u:`) —
  в нашей почте они не значат ничего.
* **По ветке не сходится** по той же причине.
* **По теме не сходится**: в ответе к теме дописали второй номер, и стоит он
  В СЕРЕДИНЕ — ни точного совпадения, ни вхождения одной темы в другую.

А номер ЗП/перемещения при этом совпадает и стоит в обеих. Он и есть примета, которая
переживает и чужие id, и дописанную тему, — поэтому добавлена четвёртая проба: номер
строки встречается в теме письма. Порядок проб: id письма → ветка → **номер** → тема
(точно, затем с запасом).

Номером считается только то, что на него похоже: в колонку «Номер» иногда пишут
произвольный текст (название поставщика), и искать по нему нельзя — подцепит чужую
ветку с этим словом в теме. Заодно первая проба теперь сравнивает id нормализованно
(через `rowIdsIntersect`): колонка хранит и `t…`, и `ts:`/`u:`, а id открытого письма
приходит то с префиксом, то без.

### Несколько подходящих строк — не ошибка

В той же теме номера **два**, и в таблице под них две строки. Кнопка на это отвечала
«Нашлось несколько подходящих строк (2) — отметьте вручную в панели»: то есть находила
всё, что нужно, и отправляла человека делать работу руками. Так было и в 2.90 — эта
часть не менялась.

Теперь кнопка спрашивает, перечисляя найденные строки, и по согласию закрывает **все**:
одно письмо часто и правда относится к нескольким заказам. Отмена — одной кнопкой на
всё, что закрыли этим нажатием. Одна строка — как раньше, без лишнего вопроса.

## «Выполнено» помечает письмо прочитанным

Письмо обработано — значит прочитано. Это верно в обе стороны: «взять на контроль»
(письмо завели в таблицу) и «Выполнено» (работу по нему закончили).

Раньше прочитанным помечалось только добавление: в `applyLabelForTopic` стояло
`wantRead = !!add`. Пока «Выполнено» работало по открытому письму, это не бросалось в
глаза — открытое письмо почта и так помечает прочитанным сама. А с тех пор как кнопка
закрывает **все** подходящие строки разом (одно письмо часто относится к нескольким
заказам), письма остальных строк человек не открывал: метка с них снималась, а
непрочитанными они и оставались.

Теперь прочитанной помечается вся ветка в обоих случаях.

## Почему письма ветки «перестали прочитываться»

При перетаскивании письмо помечается прочитанным вместе со всей веткой. Ломалось это
с двух сторон сразу.

**Дозалитые письма никто не дочитывал.** Порядок такой: метка ставится на письма,
известные на момент перетаскивания, они же помечаются прочитанными. Потом
`topUpThreadLabel` спрашивает у почты ВСЮ ветку и дописывает метку тем письмам, до
которых список не дотянулся, — у свёрнутой ветки часть писем не отрисована, а ответ
мог прийти секундой позже. Вот эти письма метку получали, а прочитанными не
становились: функция возвращала только ЧИСЛО дописанных, и дочитать их зовущему было
нечем. Теперь она возвращает и сами id, и они дочитываются.

**Список на экране показывал состояние до дозаливки.** Обновлений в этом месте два:
после простановки метки и после дозаливки. Второе приходит через доли секунды после
первого — то есть внутрь окна схлопывания, — и раньше просто выбрасывалось. В почте
письма уже прочитаны, а в списке ещё жирные. Теперь последняя просьба из очереди не
теряется, а выполняется в конце окна (см. «Одна точка обновления»).

## Когда выборка «кто носит метку» пришла пустой

Прогон метки начинается с одного запроса «какие письма сейчас носят эту метку». По его
результату отсеиваются строки, которые разбирать незачем: у выполненной или чужой
строки метку надо только СНЯТЬ, а снимать нечего, если её там нет.

Рассуждение верное — но ровно настолько, насколько можно доверять самой выборке. А
пустой ответ значит две разные вещи: «метки правда нет ни на одном письме» и «форма
запроса в этой сборке ничему не соответствует». Раньше они не различались, и это
давало тихий отказ:

1. `findMessagesWithLabel` перебирает формы запроса и на ПЕРВОЙ же, ответившей пустым
   списком, делала `break` — и запоминала эту форму на всю сессию.
2. Пустая выборка ⟹ ни одна выполненная строка не проходит отсев.
3. «Хвостов» тоже нет — их берут из той же выборки.
4. Снимать метку не с чего, ставить некому: прогон рапортует «готова, разбирать
   нечего» и не делает ничего.

Со стороны это выглядит как «закрыла строку, а метка в почте осталась» — особенно
когда строку закрывают **прямо в таблице**, минуя кнопку «Выполнено» в панели: тогда
прогон метки вообще единственное, что могло бы её снять.

Исправлено с двух сторон:

- **Пустой ответ больше не принимается с первой формы.** Он запоминается, перебор
  продолжается, и если хоть одна форма вернёт письма — верим ей. Пусто у всех — значит
  метки правда нет, и вот тогда это вывод, а не догадка.
- **Выполненные строки СВОЕЙ метки разбираются всегда**, независимо от выборки. Их
  единицы, разобрать их дёшево, а не разобрать — значит не сделать главного, ради чего
  прогон и запускают.

## Ревизия 2.92: что чинили и почему

Разбор всего кода после жалобы «2.91 стала работать хуже 2.90, а 2.90 всё ещё
недостаточно стабильна». Ниже — найденное, по убыванию тяжести.

### Регрессии 2.91

1. **Сторож сняли не только с поиска, но и с собственной навигации панели.** Коммит
   обосновывал послабление только для результатов поиска, а код снял его и с
   «идёт переход к письму» — то есть с незаконченной цепочки шагов самой панели.
   Подробнее выше, в «Одна точка обновления».
2. **Переснятие конверта стало жать кнопку почты во время прогона.**
   `refreshEnvelope` зовётся при каждом `AUTH_NO_AUTH`, троттлинг — три секунды, а
   прогон идёт в пять параллельных запросов. При протухшем конверте это давало
   нажатие раз в три секунды всё время прогона.
3. **`forceMailListRefresh` взводил отложенное действие даже после удачного
   нажатия** — почта обновлялась, и потом обновлялась ещё раз, без повода.

### Что было сломано и до 2.91

4. **`AUTH_TROUBLE` никогда не сбрасывался.** Флаг присваивался только внутри ветки
   сбоя, поэтому вставал один раз за смену и держался до перезагрузки вкладки. От
   него зависит `runIncomplete` — значит уборка «хвостов» была выключена весь день,
   каждая строка считалась неразобранной, а подсказка бесконечно советовала F5.
5. **Свой почтовый ящик определялся ровно один раз, с таймаутом три секунды.** Не
   успел (а `inject.js` узнаёт uid только из настоящего запроса почты) — и оба
   предохранителя «чей ящик» молча выключались на всю сессию: чужие id сменщицы шли
   ориентиром в поиск, а колонка «ID письма» писалась без пометки владельца. Хуже
   того, `mergeMailIdValue` в этом состоянии **портил строку сменщицы**: дописывал
   туда наши id, теряя её `t…` и `ts:…`, но сохраняя её пометку `u:`. Теперь ящик
   переспрашивается до успеха, а без него в колонку не пишется ничего.
6. **Подметание плашек копилось и грузило страницу.** Каждое «Выполнено» заводило
   свой цикл, ничто не останавливало предыдущий, потолок был пятнадцать минут, а
   каждый тик обходил **весь документ** селекторами `[class*="Label" i]`, которые
   браузер ускорять не умеет. Смена на тридцать писем — до тридцати параллельных
   циклов. Теперь цикл один, потолок полторы минуты, обход идёт по списку писем и
   открытому письму, а дешёвые проверки стоят раньше дорогих.
7. **Неоднородная нормализация id.** `keepIds` наполнялся из трёх источников
   по-разному, а `collectStrays` сравнивал сырые значения из ответа почты. Письмо с
   `mid` вида `t123` не совпадало с `123` в множестве — и живое письмо уходило в
   «хвосты», метка с него снималась молча и навсегда. Предохранители по ветке и теме
   из 2.91 это лишь прикрывали; здесь причина, и она убрана.
8. **Ранний выход прогона собирал «хвосты» без проверки полноты** — в отличие от
   основного пути. При отклонённых запросах метка снималась по неполному списку.
9. **`scheduleRefresh` в service worker жил на `setTimeout`** вопреки комментарию в
   том же файле. Запись в таблицу — как раз тот момент, когда воркер могут выгрузить:
   таймер умирал вместе с ним, и чужие правки не приезжали до пяти минут. Переведено
   на `chrome.alarms`.
10. **Мост `inject.js` отвечал в `postMessage(..., '*')` и не проверял origin.**
    Теперь отвечает строго в свой origin, проверяет отправителя и выполняет только
    модели из белого списка — универсальным прокси к API почты он больше не годится.
    Настоящей границей это не сделать (content-скрипт живёт в изолированном мире и
    секрет с MAIN-миром не разделит), но ущерб сужен.
11. **Колонка «ID письма» выключена в `defaults.js` по умолчанию**, а на ней держится
    всё опознание переписки. Панель теперь говорит об этом прямо, а не работает тихо
    хуже.

### Мёртвый код

- `strong` в `matchLabelledRow` — вычислялся тремя блоками (~45 строк, включая поход
  в кэш на каждую строку таблицы), возвращался наружу и **не читался никем**: пропуск
  давно решается фазой 0. Убран вместе с блоками.
- `untouched` / `untouchedText` в `syncAllLabels` — всегда пустые (`names = all`).
- `buildMailIdValue`, `doLabelForTopic`, `isReadingPaneMode`, `overDropTarget`,
  `getSheetId`, `DEFAULT_SHEET_NAME`, `row0` в applier — ни одного вызова.
- Счётчик «пропущено (метка уже стоит)» считался только внутри фазы 0 и врал, когда
  та не отрабатывала.

### Структура

`bulkApplyLabels` был 695 строк с вложенностью до тринадцати уровней. Фазы вынесены в
отдельные функции: `classifyRowForRun`, `verifyKnownThread`, `resolveRowThread`,
`groupResolvedByThread`, `confirmAppliedLabels`, плюс `printRunDiagnostics`,
`buildLabelRunReport`, `reportPartialThreads`, `markRowsWithoutMail`. Обработчик
«Выполнено» вынесен из `render()` в `markRowDone` / `undoRowDone`.

## Что изменилось при объединении

- Панель `background.js` больше **не** хранит колонки буквами (`colTopic`…). Теперь
  и панель, и захват читают один массив `fieldConfig` (номера колонок). Появилось
  настраиваемое поле **«Выполнено»**.
- Два попапа объединены в один; два content-скрипта подключены вместе (захват
  обёрнут в IIFE во избежание конфликта имён с панелью).
- Один OAuth-клиент и один стабильный `key` на всё расширение.
- Прежние папки `chrome-extension/` и `yandex-mail-control/` не тронуты — остаются
  как резервная копия.
